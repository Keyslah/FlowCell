Purpose
-------
FlowCell is a Windows desktop command surface for program-specific script Buttons, editable skins and geometry, popouts/fans, program bridges, layouts, bindings, and local automation.

Current Architecture
--------------------
- Repository skill `.agents/skills/git-safe-sync/SKILL.md` documents preserving local work with a backup branch and safety commit, then fetching and merging remote changes without destructive recovery or force pushes.
- Blender action waits pause their timeout while that Blender process has a visible native dialog, allowing first-run Orca settings to be answered; actual response timeouts no longer report that Blender is closed.
- Blender Theme Absorb returns only colors available in the current Blender version; unsupported RNA fields leave staged buckets unchanged instead of failing the page response schema. Theme package version 3.0.12.
- Windows organizer project preparation accepts Microsoft's cloud-storage directory tags, including leftover OneDrive markers, while continuing to reject junctions, symbolic links, and unknown reparse tags. Setup Organization contribution version 1.3.3.
- Core dialogs and installed pages fit their complete native frame inside the monitor work area before showing, including high-DPI displays and restored positions. Minimum sizes are capped to the available client area.
- Runtime data and Programs roots use canonical filesystem identities at startup, keeping owned-source quarantine comparisons consistent through Windows AppData redirection.
- Illustrator declares Align and Rotate as optional Add Program contributions with a dedicated Toolsets destination, so Add everything installs them without relying on the currently selected panel.
- Illustrator SVG export groups a single selected path before applying the live Pathfinder effect, avoiding Illustrator's blocking ungrouped-artwork warning.
- SVG handoff completion uses extended Windows paths for atomic status-file writes, including temporary names exceeding the Windows PowerShell 260-character limit.
- Generated Windows organizer Buttons honor the installed FLOWCELL_LOCAL_ROOT, and organizer staging computes SHA-256 through .NET without depending on PowerShell module discovery.
- Blender add-on deployment explicitly creates the empty ManagedActions runtime directory required by first-install bridge discovery; Git-tracked program ZIPs cannot carry empty directories. Illustrator's standalone action helper defaults to the current v2 bridge pipe and matching start mutex.
- Background Blender jobs do not publish the shared GUI bridge status, so importing a live-tool module in a batch job cannot replace the running Blender window's process identity.
- Blender declares every catalog toolset as an optional Add Program contribution to its existing toolset panel, so Add everything includes the complete tested toolset collection on fresh installs.
- The development release launcher preserves its executable-path lookup as an array, including release-only installations, so strict PowerShell process discovery can safely distinguish this build from another installed copy.
- Illustrator bridge containment compares final filesystem paths for both Local Scripts and the requested file, matching native Rust path resolution through redirected Windows AppData and continuing to reject junction escapes.
- Installer releases use Tauri NSIS per-user setup and bundle the tracked backend, AutoHotkey runtime, helpers, config/assets and license/source notices. Installed startup resolves resources beside the executable, starts preflight and the headless backend, and keeps all writable state in `%APPDATA%\FlowCell\local`; `FLOWCELL_LOCAL_ROOT` is a direct override. Development and existing portable defaults remain unchanged.

Six tracked packages (including Fusion 360) ship optional ordinary Update Git Scripts contributions in Files. Runner-compatible owned entry points invoke the packaged catalog-only downloader; local conflicts/unknown files survive, unchanged upstream deletions are recycled, and staged blob-verified downloads have rollback journals. - Setup Organization is a folder-tree editor. Its page has two panes: `Folders` is an Explorer-style tree the user adds to, renames, deletes, and can fill from any real folder via `Load tree from folder…` (read-only against the source, breadth-first, with an optional folder cap defaulting to 12); `Files` owns the selected folder's assignments — file-group checkboxes with per-group `edit` (add/remove that group's file types under its stable ID, so every profile referencing it follows) and inline creation, a direct extension field, a `Collect all other files here` catch-all toggle, an `Ignore this folder` toggle, and `Apply`, which commits the selection so returning to that folder shows it again. At most one folder may be the catch-all and it may not also be ignored; both rules fail closed at save. Shared groups split into plain file groups (`Images`, `3D` - neutral/interchange formats only) and program file groups (`Blender`, `Illustrator`, `Fusion 360`), with no extension in two groups. A profile also carries `programFolders`: each entry binds a program file group to a root-level folder named after the group, created only when at least one matching file is present anywhere in the scan, and claiming that group file types ahead of every ordinary folder route. An entry may name another saved profile to build inside that folder; when that nested profile assigns the same program group to one of its own folders, that folder becomes the destination and overrides the program folder root. A profile cannot nest itself, cannot reference a non-program group, and cannot be deleted while another profile nests it. Roles, program folders, snapshot/live versioning, root bindings, resolution modes, and runtime ambiguity prompts are gone; a profile that assigns one extension to two folders is rejected at save. Profile names are unique because the name becomes the installed Button's label, and deleting a profile still referenced by an installed Button fails closed.

Pressing it resolves a target folder from its argument or the clipboard, validates any existing project marker before mutation, creates missing active profile folders, scans recursively, moves each file to the first folder in profile order claiming its extension, never overwrites, leaves unmatched files and current ignored subtrees untouched, performs enabled Recycle Bin cleanup, writes an undo journal, and atomically rewrites the project marker.

When enabled, the previous marker's ignored paths are the only whole-tree cleanup candidates: a path is recycled without routing its contents only when the current profile no longer owns it. Missing markers produce no stale candidates, while invalid/unsafe markers, unsafe existing stale paths, and unresolved current program/nested-profile ownership fail closed before mutation. A failed stale-tree recycle leaves the previous marker in place so the next run retries it. Button Host And Skin Contract
-----------------------------
- The functional host owns interaction state, keyboard/pointer behavior, accessibility, validation, dispatch, and lifecycle.
- A placement may own one host-run activation cycle containing at least two ordered logical states; two states are the ordinary On/Off toggle, while any larger count is the same cycle model. State 1 is the initial session state. Each state owns one stable ID, label, `press`/`hover`/`release` advance trigger, one canonical latched resting visual supplied by the assigned skin, and optional partial-JSON `resultMatches`. Ordinary cycles advance locally and wrap to State 1. A result-mapped cycle instead waits for an authoritative action response; each newly opened expanded Tool Set resets its result-mapped placements to State 1, and later child responses set the exact index rather than guessing the next one. A declared package-owned read-only `stateQuery` is not run automatically during open/expansion. The host that receives an authoritative response applies it locally before broadcasting it to other mounted copies, so a Pop does not remain at State 1 merely because cross-window transport has no active Main coordinator. Real Hover, Pressed, Held, Play, and Release input temporarily renders its nonempty authored skin state, then settles back to the latched visual; an empty transient section falls through to the next authored input state or the configured resting visual, keeping a completed Hover target continuously applied instead of replaying its transition. A placement-owned visual-state map may key configured cycle-state IDs to route those transient triggers to different authored visuals without changing the stable cycle visual, index, label, or authoritative result matching. Once an authored Pressed, Play, or Release presentation is requested, native window preparation must commit it to the skin before a fast pointer-up or action result may supersede it; finite motion then completes from the Web Animations completion signal before the newest requested appearance is applied. Functional Error and Disabled remain the highest-priority desired visuals without interrupting already-latched finite motion, and edit-focus selection does not replace a configured visual. The current index remains session-only and keyed by placement ID across mounted windows; response mappings and query declarations do not persist the live index or alter skin source. One press/release gesture can advance at most once even when another mounted copy advances in between; cancel is not release, and a real hover entry advances at most once until leave. Main's selection-only script Buttons may advance a Hover state on real entry, keep ordinary single selection clicks inert, and synthesize one Press/Release gesture only after successful double-click execution.
- The Skin Editor's `Button States & Behavior` section exposes a state count from 2 through 64, one Advance on dropdown per state, then a State and skin-dependent Visual state dropdown with an immediate real renderer preview. A result-mapped state adds one compact `Action: value` line whose tooltip shows its complete response matches. The visual list contains Base plus canonical sections authored by the active working skin; choosing one changes only that placement cycle and never rewrites skin code. Button Text uses those exact logical states for per-state labels and previews the selected state's assigned visual immediately. Save Settings persists the cycle. Button Text's bottom `Apply All` remains text-only and requires changed cycle IDs to be saved first. It saves each shared Button Tooltip regardless of cycle configuration; with a configured cycle it saves only placement-state labels and preserves the shared base Button label, while without one it saves the base label and mirrors it into legacy activation-state labels so the compatibility runtime and preview agree. Legacy Button-owned activation behavior remains readable only as compatibility fallback for placements without a configured activation cycle.
- Main's Button section separates selection from execution: one ordinary click toggles that exact script, macro, or Tool Set owner in the current multi-selection, latching the skin's authored pressed state with no host outline unless that placement owns a cycle whose selected visual remains authoritative, while a double-click runs that Button's primary action directly on Main. Main suppresses the Button's authored hover/press/click actions and activation effect for the ordinary selection gesture, including Buttons whose `pressDown` event normally owns execution. `Fan (N)` retains selection-driven Fan creation/opening. `Open Pop`, immediately left of `Pop`, opens a native picker in the selected `<Program>/<Panel>/Pop` settings folder and opens the selected regular or Tool Set settings file as an isolated temporary draft window; it does not load into an Editor surface or mutate or commit canonical Button state. Its ordinary `button-popout` window participates in Save Layout with its selected file, choice, panel owner, and semantic bounds, so Load validates and rebuilds that draft at its saved position before replacing the current managed layout. Main remembers only `{ path, choiceId }` in machine-local storage under the stable panel-owner Button ID. `Pop` reloads and opens that panel's last-used file independent of Main selection; when none is remembered, it creates or reuses a canonical starter Pop containing that panel's installed single-script Buttons and opens it. Once popped out, an ordinary click runs the Button through its normal runtime host.
- Skins are render-only and isolated. They cannot execute actions, mutate state, own bindings, or define source targets.
- Every skin contains exactly one measurable `[data-core]`, zero or one `{{label}}` token inside it, and optionally one `data-hit-shape` descendant when the semantic core is a larger layout wrapper than the intended pointer shape. Textless and animation-only skins receive no synthesized text or fallback face; the saved Button label still supplies the accessible name.
- A skin that supplies a complete alternate appearance for a logical Button state is authored as one paste-ready composite: every alternate face stays inside one stable `[data-core]`, and state declarations or CSS custom properties reveal the intended face. A skin may never embed another functional Button, another `[data-core]`, a per-state hit target, or a runtime skin swap for an alternate state; the optional single `data-hit-shape` remains stable across every state.
- Skin authoring uses a neutral render-only core whose resting body matches the intended clickable footprint. Browser controls are forbidden inside skin markup. Newly authored packed skins may not invent transparent layout gutters, while literal conversions preserve the source control's complete visual box model, including authored padding or transparent depth space that positions its face/base/press travel; only outer demo/page spacing is removed. Inherited source typography is frozen to its resolved pixel font size/line height so natural geometry stays identical across Editor/Main/Pop/Fan. Pseudo-elements become equivalent pointer-inert real layers, absent source states stay empty, and a color-only request changes no geometry or unmentioned visual value.
- The compiler lifts the core's inline `style` into a lowest-priority `[data-core]` rule so ordinary state declarations override that core; nested visuals remain literal and consume custom properties initialized in Base. Skin paste headers tolerate whitespace and case.
- New skins, conversions, and complete replacements include every canonical paste header, including empty sections that clear stale keyframes or state. The repo-local `skin-author` preflight compiles the current parser/validator, requires the full replacement header set, requires an effective pixel font size and pixel line-height for labeled or `em`-sized cores, and rejects inherited core metrics or any semantic diagnostic before a paste block is returned. Original skins require a painted-footprint check; conversions require source/result rest-and-state geometry comparison because static validation cannot infer visual equivalence.
- The Skin Editor's Button Size section keeps width, height, and sizing behavior in a working preview until an explicit assignment. Each newly selected or replaced working skin starts with Responsive as its pending policy while preserving the placement rectangle. Loading, pasting, or directly editing skin source first renders and measures that working skin at its natural core size; it does not inherit the selected placement's dimensions. Selecting Responsive, Proportional, or Stretch changes only the pending policy and never changes width or height. A width/height edit changes only the working preview, while `Assign Size`, `Assign Size to Panel`, or releasing the blue canvas resize handle is an explicit geometry commit. Responsive constrains `[data-core]` to the exact independently requested host width and height, aligns its authored resting offset to the placement origin, and skips root scaling so authored flexible contents may reflow; fixed nested artwork may overflow and never triggers an automatic fallback. Proportional scales the complete authored root uniformly from its measured natural core and aspect-locks explicit resizing from that natural ratio, even when an older placement box has already been distorted. A ratio-locked skin is therefore proportional-only, not incapable of proportional sizing. Stretch performs explicit independent X/Y root scaling and may distort typography, corners, and effects. An ordinary canvas move changes position only. Validation
----------
- Frontend/Tauri changes: run the relevant frontend build; use `flowcellbackend/helpers/Start-FlowCellFrontend.ps1` with `-ForceRestart` when the running frontend must refresh. A fresh helper launch arms a unique Button-bootstrap health marker and succeeds only after Main clears it; a fresh nonempty bootstrap error, early process exit, or bounded wait timeout fails the handoff instead of reporting a broken runtime as healthy.
- Rust changes: run `cargo check` plus focused tests.
- AutoHotkey changes: validate with AutoHotkey v2 and restart the hidden backend.
- PowerShell changes: parse-check touched scripts and run the narrow behavior test when practical.
- Blender source/bridge changes: compile-check Python where applicable and verify after add-on reload or Blender restart.
- Documentation-only changes: validate headings, links/paths, and stale-term removal; no application build is required.
- Portable program ZIPs contain only Git-tracked package files, require a tracked program manifest, and reject manifest-declared mutable folders, reparse points, containment escapes, and unsafe archive members; the Core ZIP contains no `Programs/` payload.
