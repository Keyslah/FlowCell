FlowCell Program Summary
Last updated: 2026-07-05

Purpose
-------
FlowCell is the desktop frontend, command host, program folders, local runtime state, and Blender bridge workflow.
The backend/runtime folder is `flowcellbackend/` (renamed from the former top-level `FlowCell/` folder). It contains `FlowCellBackend.ahk`, `FlowCellCommandBackend.ps1`, launch helpers, runtime config, and ignored local state under `flowcellbackend/local/`; root launchers, Tauri backend resolution, packaging, Blender/Illustrator/Windows helper scripts, and docs now resolve that folder name.

Current frontend state
----------------------
- Dynamic Organization has a role-based backend and frontend resolver. Setup Organization opens the managed `organization-setup` Tauri/React window by intercepting the panel script filename in main-panel activation, the shared panel-script runner, and the backend response path, while the full PowerShell setup UI remains a standalone fallback. The left sidebar is two separated panels side by side: a Root folder panel (root rail + the root folder tree + Delete folder / Undo) and a Load profile panel (load profile rail + the loaded profile's tree + its own Delete folder / Undo). Only one folder is selected at a time across both trees — selecting a folder in one tree clears the selection in the other, so a single "active folder" drives the editor. Delete folder sends the selected folder to the Recycle Bin (the on-disk project folder, or a folder in the saved profile skeleton; for an unsaved scratch profile tree it just drops the folder from the in-memory list), and Undo reverses the last folder add/delete (restoring deleted folders from the Recycle Bin best-effort). The root rail's Apply profile button builds the loaded profile's structure into the selected folder — the root (also writes the profile) or any subfolder (folders only). Clicking a folder in either tree shows that folder's assigned roles/folders on the right (the editor card follows the active selection, so you can view and edit a profile folder's assignments too). The Load profile rail's Copy root to profile button mirrors the current root folder's folder structure into the profile section as an unsaved scratch tree you can view/edit before saving it as a named profile; the disk-writing project-only actions (Delete folder under the project tree and Apply profile) stay scoped to the project tree, while Add Folder targets whichever tree's folder is active. The footer has Apply to tree (write the profile to the root folder), Apply to profile (save the current setup into the loaded profile, to build it up incrementally), and Apply & rescan. Roles are assigned from a Role dropdown and list as compact rows (Name | file types | Edit / Unassign / Delete) showing every assigned file type; folders added to the selected folder appear in the same list (tagged "Folder"). Program folders (those carrying file types) are grouped under their build root `01 src` — where the apply step actually creates them (e.g. `01 src/Illustrator`) — so they show when `01 src` is selected rather than under the root folder, even if the saved rule stores a bare name; plain folders and folders with an explicit parent keep their literal parent. Add Role opens a popup with a Role name / File types row, grouped file-type picker buttons (Images, 3D Files, Illustrator, Blender, Fusion 360, GCode/CNC, Reference/Documents), an Add File Types action, and Save File Group which stores reusable custom groups in browser localStorage. Add Folder (next to Add Role) opens a popup that adds any folder name to the active folder in either tree (file types optional): Add folder creates it immediately and rescans so it shows in the tree; Add when files match makes a conditional rule created on apply. Where "Add folder" materializes depends on the active tree — a project folder creates it on disk under the root folder, a loaded saved profile folder creates it in that profile's on-disk skeleton (so it sticks), and an unsaved "copy root to profile" scratch folder adds it to the in-memory tree (kept on Save Profile). Because the profile section is the source of truth for a loaded/scratch profile's folders, Save Profile / Apply to profile re-save that tree (not the project tree) so folders added there are never wiped. The popup also lists saved profiles — clicking one builds that profile's structure into the selected folder. Folders with file types show a substructure preview in their assigned-list row (01 live / 02 snapshots / 03 archive / 04 trash) so you can see what will be built. A direct File Types input assigns types straight to the selected folder. The footer Apply to tree button writes the profile to the current root folder. The Don't Remove Files control is rendered natively in the React setup page and saves selected protected folders into the profile, so picking a new root folder no longer relies on runtime DOM patching. The preset `unknown` role must be assigned to a scanned folder before saving (shown as a bottom warning, not a popup); unmatched loose files fall back to `unknown`, while files matching multiple roles open a scoped file/run/project choice prompt.
- The per-project profile is a single visible file `<root>/organize-folder.profile.json` (legacy `.flowcell/organization-profile.json` is still read as a fallback and migrates on the next save); both the Rust commands and `Dynamic-OrganizationCore.ps1` use it. It is written as UTF-8 without a BOM, and the Rust reader strips a leading BOM so PowerShell-written profiles still parse. Save Profile stores a named, reusable copy in two places: a clean empty folder skeleton (folder structure only) under `flowcellbackend/local/Folder Trees/<name>/` and the profile data under `flowcellbackend/local/Folder Tree Profiles/<name>.json`. Load profile loads a saved profile's rules into the editor without changing the project root; Apply profile to root builds that profile's folder structure, writes the profile there, and applies conditional program-folder routing without deleting or overwriting files. Make button generates the apply-profile script (`Programs/Windows/Windows Git Scripts/Files/apply_profile_<slug>.ps1`, backed by `Programs/Windows/SupportScripts/Apply-OrganizationProfileCore.ps1`) and drops it straight into the Windows `Files` panel as `<ProfileName>.ps1`, so a panel button named after the profile appears (reselect the Files panel to refresh); clicking it applies the profile to a clipboard folder path. The name `setup_organization` is reserved for the launcher button.
- The starter profile assigns nothing to any folder. It has the required `project_root` and `unknown` presets plus three default roles available in the Role dropdown — Images, SVG, 3D (each with its file types, unassigned) — and no program folders. The four program defaults (Illustrator .ai/.ait, Photoshop .psd/.psb, Blender .blend/.blend1, Fusion 360 .f3d/.f3z) are only quick-fill presets in the Add Folder popup and are never auto-added. Added folders persist as `programFolders` entries. Applying a named profile (`Apply-OrganizationProfileCore.ps1`) places each program under `01 src` beside `00 assets`, names it `NN <Program>` (reusing an existing unnumbered match), and always adds `01 live`, `02 snapshots`, `03 archive`, `04 trash`. Only working files inside `01 src` plus loose files dropped at the project root (which get filed into `01 src`) are eligible to be routed — every `01 src` sibling (`02 builds`, `03 releases`, the big top-level `04 archive`, etc.) is left untouched, and any program's own `02 snapshots`/`03 archive`/`04 trash` (with or without a number prefix) is skipped so already-filed, archived, or trashed files are never pulled back into `01 live`/`02 snapshots`. Within a program, files are grouped by extension then by family name (`Get-DuplicateInfo` strips trailing copy/version/final markers): the newest member of a versioned family goes to `01 live` and older members go to `02 snapshots` as `<base> (Snn)`; everything else goes straight to `01 live`. Moves are verified and non-destructive (conflicts recorded, never overwritten).
- The main-page Add Program flow accepts either a pasted EXE path or the folder containing the EXE; leaving the paste prompt blank opens a folder picker. The desktop host resolves the primary executable, including preferring `blender.exe` over Blender launcher/helper executables, before registering and bootstrapping the program.
- The main FlowCell window (frameless, `decorations: false`) supports hold-Space-and-drag to move it, the same convention used by the toolbox/popout windows: holding Space sets a grab cursor, and dragging while held calls `startDragging()` on the current window. The handler lives directly on `MainPage`'s root `<main>` element (`onPointerDownCapture`), so it does not interfere with normal button clicks when Space is not held.
- Windows program panel scripts run without first activating `explorer.exe`: the backend treats Windows/explorer/DOpus-backed generic programs as `windows_generic`, so scripts such as monitor toggles can run without pulling a File Explorer window back to the foreground.
- The default Ctrl+Shift+F2 "single-monitor" shortcut (auto-bound to `Programs/Windows/Panels/Utility/Toggle Monitors.vbs`) is now persisted to `flowcellbackend/local/bindings.ini` the first time `FlowCellBackend.ahk`'s `EnsureDefaultSingleMonitorBinding` restores it, instead of staying in-memory only — previously the Binds UI (which reads `bindings.ini` directly) always showed it as unbound even though the hotkey worked. `ShortcutManager.SaveToDisk()` also now re-normalizes the file to UTF-8 after writing (AHK's `IniWrite` recreates files as UTF-16, which the Rust `read_bindings_file_state` strict-UTF-8 reader cannot parse at all). The frontend's own fallback default-binding resolver (`resolve_single_monitor_binding` in `main.rs`) was pointed at a stale, nonexistent `Programs/Windows/toggle_monitors.ps1` path from an older version of this feature; it now points at the same `Toggle Monitors.vbs` the AHK side uses. Separately, an unrelated legacy "Dummy Monitor Toggle" feature (the predecessor to Toggle Monitors) left orphaned backup files in `Windows Local Scripts`/`ScriptDump`, an orphaned `__pycache__` entry, and a dead Windows Startup shortcut pointing into an unrelated `computerideas` repo; all were removed (Recycle Bin), along with stale `%LOCALAPPDATA%\ToggleMonitors\` snapshot/profile leftovers from that era.
- Windows PowerShell launches are hidden across the shared runners: the AutoHotkey command backend always runs `.ps1` panel scripts with `-WindowStyle Hidden` plus AutoHotkey's hidden launch flag, the Tauri PowerShell output helper uses `CREATE_NO_WINDOW`, the FlowCell VBS frontend/backend launchers pass hidden PowerShell startup flags, and STA self-relaunching Utility scripts use `ProcessStartInfo.CreateNoWindow` so no blue PowerShell console should flash during panel-script actions.
- The Windows Utility panel includes `Temp_Shots.vbs` as the visible Temp Shots button (`Programs/Windows/Windows Git Scripts/Utility/Temp_Shots.vbs`, mirrored into `Programs/Windows/Panels/Utility/` and `Programs/Windows/Windows Local Scripts/`) so FlowCell launches it through `wscript.exe` without a console and without a space-bearing script path. The launcher starts `Temp Shots.ps1` hidden and returns immediately for normal captures so shortcut bindings are not blocked while Windows screen snip is open; validation mode still waits for an exit code. After a Temp Shots folder has been selected, the hotkey path opens Windows screen snip directly from the resident AutoHotkey backend, then starts the hidden PowerShell saver in clipboard-wait mode so PowerShell startup no longer delays the snip overlay. The PowerShell implementation clears older Temp Shots runner processes before waiting, prompts once for a screenshot destination folder, stores that choice under `flowcellbackend/local/windows/temp-shots/temp-shots.config.json` plus a no-BOM `temp-shots.folder.txt` fast-path cache, then saves each captured clipboard image as a timestamped PNG and writes the result to `flowcellbackend/local/logs/last_action_status.txt`. FlowCell reads `flowcellbackend/local/bindings.ini` with a BOM-tolerant parser before shortcut registration so BOM-prefixed binding files still load saved hotkeys.
- The Blender Theme toolbox stages theme buckets from an image, absorbed Blender theme values, dark/light presets, per-bucket swatches/eyedroppers, hex fields, and per-bucket apply buttons. The top theme `Browse` now samples the chosen image, copies that same path into the Place Picture field, and immediately runs Place Picture in Blender; the bottom Place Picture row remains separate and still has its own `Place Picture`, picture path input, `Browse`, `Startup`, and `Clear` controls that do not change theme buckets. The `Startup` button saves the current Place Picture image to the global startup state file (`flowcell_theme_startup_state_v1.json` in Blender's CONFIG dir); on each Blender launch `flowcell_actions.py` re-registers the `load_post` restore handler and polls, calling `read_place_picture_runtime_state` then `restore_project_startup_state` on the `flowcell_custom_theme` action, whose `_restore_project_startup_state` reapplies the saved picture. Two bugs kept this from working: (1) a misplaced grid-clamp loop had been pasted into `_ensure_project_theme_restore_handler_registered_from_action` (referencing `place_picture_state`/`state`, out of scope there), so every save raised a swallowed `NameError` before the handler could register — that loop was moved into the state-normalization function (where those names exist and it also clamps `grid_distance_m`/`grid_far_spacing_m`); and (2) the theme script had **forked across its copies** — the generated runtime/installed copy had been hand-edited to add the restore subsystem (violating the "never edit ManagedActions as source" rule) while the `Blender Git Scripts/toolset/theme.py` source lagged behind and never gained it, so the copy Blender actually ran depended on which stale generation was installed. All four copies were reconciled to one canonical version (source `Blender Git Scripts/toolset/theme.py` == `ManagedActions/flowcell_custom_theme.py` runtime == `Blender Local Scripts/theme.py` backup == the installed `scripts/addons` copy, byte-identical): the complete restore subsystem + project/global startup-state model is kept, the dead `_remember_theme_bucket_state`/global-only-state helpers were dropped, and the `# FLOWCELL_CHILD` header keeps the current Save Buckets/Load Buckets labels. Going forward only `Blender Git Scripts` is edited and re-deployed via Add Script (which copies the source verbatim into `ManagedActions`); after any of these changes Blender must reload the FlowCell add-on / restart for startup restore to take effect. The single bucket Apply buttons route through the Blender theme action's `apply_theme_bucket` handler, which now delegates to the exact same pipeline as the main Apply (`_apply_theme_from_photo_manual_colors`) after overriding only that bucket's hex in the staged palette the panel already sends — so a single bucket applies to every Blender theme field the full Apply feeds from that bucket instead of a hand-maintained subset that had drifted behind the full apply (fixing the bug where a bucket applied to only part of what the main Apply later completed); re-asserting the other staged colors is a visual no-op in the normal workflow because they already match the live theme. The old visible Grid button and near/distance/far grid spacing fields are no longer shown, while the Blender bridge still accepts the stored grid payload values internally for compatibility. The custom-action sync restores configured bundled Blender actions from the repo registry before regenerating the live registry, so the `flowcell_custom_theme` button is restored from its source-backed runtime entry without relying on the old `custom_hdri_world_tools` alias. Place Picture overlay drawing is generation-gated, and Clear invalidates active/stale generations so the background, fake grid, and fake gizmos stop drawing after cleanup. The theme status message is a short-lived toast that clears itself after a few seconds, and the native theme toolbox window auto-fits to the measured visible toolbox content on open so the transparent area below the controls does not block desktop clicks. Save Buckets opens a single native save dialog (pre-filled with a default theme file name) instead of also showing a separate name prompt. Refill re-rolls role colors by sampling only from the stable sampled palette and no longer folds the current role colors back into that palette, so repeated refills stay varied instead of drifting toward grey. The top theme-path row also has `Save` and `Open` buttons to the right of `Refill` (and its image path field is rendered smaller): `Save` prompts for a name and writes a theme "package" into a single `<name>` subfolder of the FlowCell `blender_themes` folder — the actual image bytes plus the staged bucket colors, not just the path — containing the copied image(s) (kept under their original file names) and a `<name>.flowcell-theme-pack.json` manifest (bucket colors + image file-name refs); one image is stored when the theme (buckets) image and the Place Picture image are the same path, two when they differ. `Open` is a dropdown control (with ‹ › cycle arrows on either side) instead of a plain button: the dropdown lists the saved theme packages under `blender_themes` (enumerated by the new `list_blender_theme_packages` Tauri command, which reads each `<name>/<name>.flowcell-theme-pack.json` manifest's display name) plus a `Browse for file...` entry, the arrows step to the previous/next saved package, and selecting/cycling restores both the bucket colors and copied image paths via `load_blender_theme_package`. Both cycling with the arrows and picking an entry from the dropdown list load the package and then apply the bucket colors to Blender (`apply_theme_from_photo_manual_colors`) and, when the package carries a background image, re-run Place Picture (`place_picture`), so selecting or stepping through saved themes updates the live Blender theme and viewport picture. The trigger label shows the active package name (defaults to `Open`); saving a package selects it as active and refreshes the list. Only the `Browse for file...` path opens a native file dialog now, and it runs through `runWithWindowForemost` (focus + force-topmost, then re-register scoped topmost) rather than the eyedropper-style `runWithScopedTopmostSuspended` — suspending scoped topmost dropped the theme window below Blender so the parented dialog opened hidden behind Blender; keeping the window foremost surfaces the dialog on top. These are backed by the `save_blender_theme_package`, `load_blender_theme_package`, `list_blender_theme_packages`, and `resolve_blender_theme_root_path` Tauri commands (separate from the JSON-only `Save Buckets`/`Load Buckets`). While a native color/eyedropper picker is open the theme window stays fully suspended from the scoped-topmost worker so the eyedropper works over any monitor (including Blender's) without the taskbar/topmost flicker. The capture-phase shell pointer handler no longer re-registers scoped topmost on the click that opens a color picker (that registration used to race and beat the picker's suspend), the window-focus handler no longer re-registers while a picker is open, and scoped topmost resumes only when the picker actually closes (color input blur, Escape, or a click back inside the window). The scoped-topmost worker is now idempotent: it only re-issues the native always-on-top/SetWindowPos calls when the resolved state changes (target gains/loses foreground, cursor crosses the taskbar, or owner change) instead of every ~180 ms poll, which stops the continuous z-order churn that flickered the taskbar while Blender was foreground. Applying the Light Theme preset (and any light-mode refill/darkness-profile result) now forces every text bucket to pure black (`#000000`) so light-theme labels stay readable. The theme-actions row also carries a darkness slider directly beside the Light Theme chip (left = darkest, right = lightest, persisted in `flowcell.themeToolbox.darknessLevel.v1`, default 0.3): releasing it re-samples every tone bucket around that level via `buildLeveledThemeRoleAssignment`, which interpolates each bucket between its dark and light preset target (`DEFAULT_DARK_TONE_TARGETS`↔`DEFAULT_LIGHT_TONE_TARGETS`) with small per-bucket jitter, so the whole theme moves lighter/darker while each bucket keeps its own relative lightness (backgrounds stay the darkest elements, highlights the brightest) and derives dark/light text from the level (≥0.5 → black text). To keep the result colorful instead of dull/greyed, buckets no longer hit their target brightness by mixing toward black/white (which desaturates); a new `colorizeHexToLuminance` (with `rgbToHsl`/`hslToRgb`) moves lightness in HSL space while preserving hue and holding saturation to a floor (highlights get a higher floor), and each bucket gets a per-bucket hue rotation — a small nudge for colored samples, a fresh full-wheel hue for near-grey samples — so a small image palette spreads into many vivid, varied colors on each drop. Dragging only re-stages the slider value; releasing stages the resampled buckets on the page (Apply still sends them to Blender), matching the Dark/Light preset buttons. The theme toolbox window (only this tool window) now has a title-bar header at the top of its content card carrying the tool label plus Minimize / Maximize (toggles maximize/unmaximize via `isMaximized`) / Close buttons wired to the Tauri window APIs; the header doubles as a drag region (pointer-down anywhere but the three buttons calls `startDragging`, in addition to the existing Space-drag), and it is part of the measured content so the auto-fit sizing accounts for it.
- Blender Add Script treats `Programs/Blender/Blender Git Scripts` as the source library and `ManagedActions` as generated installed runtime output. Add Script accepts ANY Blender source that exposes `run_flowcell_action(context=None, data=None)` — a single script, a toolset, or a thin wrapper whose `run_flowcell_action` calls `bridge.execute_bridge_operator(...)` — and installs, deletes, and re-adds them all through the same path, so every button (including the formerly "built-in" ones like snapshot/sort/back/trash) is a first-class Add Script citizen. The old `FLOWCELL_BUILTIN_ONLY` marker, the bridge-wrapper rejection, and the installer's built-in action/description maps were removed; bridge wrappers work because the referenced operator lives in the installed add-on (`flowcell_bridge.execute_bridge_operator`). Add Script records `pythonPath` as the runtime copy and `sourcePythonPath` as the real selected source, preserves `FLOWCELL_KIND`/`FLOWCELL_CHILD` metadata, and the bridge prefers registered scripts before built-in compatibility fallbacks. The bundled Blender config/registry is pruned to the active source-backed custom actions; old `custom_*`, stale `_2`/`_3`/`_4`, util alias, panel-copy, and bridge-only ManagedActions variants are removed instead of kept as hidden runtime source. Alignment Tools and Flatten/Revolve are self-contained in `Blender Git Scripts/toolset/` and mirrored into checked-in runtime copies. Deleting Blender buttons calls `delete_blender_action(action_id)`, removing config entries, registry entries, unreferenced generated ManagedActions files, and stale same-family variants before verifying no dangling config or registry references remain. Blender may need an add-on reload/restart after Add Script, delete, registry, bridge, or ManagedActions changes. (2026-06-30 the installed add-on's `ManagedActions` had drifted to 86 `.py` files from repeated Add Script runs; it was pruned back to the 24 registry/button-backed actions — old `custom_*` engines like `custom_hdri_world_tools.py`, now-built-in action copies such as `snapshot`/`sort`/`back`/`trash` and their `_2`.. dupes, and `util_boolsafe_*` variants were recycled — and the repo deploy copy lost 6 stale `_N` dupes, matching the pruning policy above.)
- (2026-07-03) Blender custom actions now dispatch per-file ONLY. `Sync-BlenderCustomActionCode.ps1` no longer generates the `perform_flowcell_custom_*` wrapper section into `flowcell_actions.py` (it strips any leftover auto-generated block instead); it normalizes every registry entry so `pythonPath` is the action's own `blender_bridge_flowcell/ManagedActions/<action>.py` (copied from `sourcePythonPath` when the wrapper is missing, never `flowcell_actions.py`) and `functionName` is the wrapper's real entrypoint (`run_flowcell_action`/`main`/`perform_*`). This repaired the live AppData registry, where 15 entries (rename selected, snap x5, cone/cube/cylinder/sphere/triangle, cura, orca, obj import, lithophane, origin geo, split, transform, slicer) still pointed at monolith functions deleted by the 2026-07-01 cleanup, leaving those buttons dead; slicer's never-deployed wrapper was copied in. The last old-name references were converged onto the current action ids (`flowcell_custom_alignment_tools_2`, `_flatten_revolve_2`, `_remesh_2`, `_smart_axis_3`, `_xyz_dimensions_2`) in the five toolset panel items and `Programs/Blender/config.json`, and six orphaned deployed wrappers (the old non-suffixed toolset copies plus `flowcell_custom_rotate.py`, unused because rotate runs from its repo source via the legacy-compat entry) were recycled. Blender must reload the FlowCell add-on or restart once to drop the stale pre-cleanup in-memory module; after that, registry/wrapper changes are picked up per request with no reload.
- The Blender Files panel Save STL, Cura, Orca, and generic Slicer buttons export selected mesh objects to the active project's organization-profile destination for `.stl` files: the matching program folder's `01 live` folder when `.stl` is assigned to one program folder, the matching/remembered role folder otherwise, or `01 src/00 assets/03 3d` when no profile route exists. The exported path returned by Blender is the exact file path passed to FlowCell's slicer launcher.
- The Blender Files panel Cura and Orca buttons export selected mesh objects to STL, then FlowCell uses a confirmed slicer executable path. On first use, or when the saved path no longer exists, FlowCell prompts to confirm the auto-detected slicer EXE or choose a different EXE; confirmed paths are saved separately in `flowcellbackend/local/cura_launcher.json` and `flowcellbackend/local/orca_launcher.json` for later launches. If Blender is not running, FlowCell stops before the slicer prompt and tells the user to open Blender first.
- A generic Slicer button (`Programs/Blender/Blender Git Scripts/Files/slicer.py`) exports selected meshes to STL and asks FlowCell to launch a user-chosen slicer EXE. FlowCell treats its `slicer_id: "slicer"` response as a generic launcher instead of coercing it to Cura or Orca; it accepts any chosen `.exe` and passes exported model files through the same launcher command path as the Cura/Orca buttons. FlowCell hands the exported STL paths to the slicer by launching the chosen slicer EXE with those paths as arguments and lets the slicer's own single-instance setting decide where they land — its running window when single-instance is enabled, otherwise a new window — so the model always loads. FlowCell does NOT force a `--single-instance` flag: when the user's slicer has that option turned off (e.g. OrcaSlicer's default `single_instance: false`), forcing it makes the launch try to hand off to a window that is not listening, so the files are silently dropped and nothing loads. FlowCell also no longer posts a cross-process Windows file-drop/`WM_DROPFILES` message, which silently failed — the drop handle is only valid inside FlowCell's own process, so the slicer never received the files even though the post reported success. This does not change the Blender-owned button window's scoped topmost behavior. Each slicer button instance owns its own executable assignment, keyed by program/panel/file in browser localStorage (`flowcell.slicer.buttonAssignments.v2`, so stale v1 assignments no longer suppress first-use prompts). The first click on a button with no assignment opens a native slicer chooser with spaced one-click buttons labeled only by slicer name for the script-detected slicer, recent slicers, and detected installed slicers from standard install roots plus Windows installed-app metadata, plus a `Browse...` button for any other `.exe`; chooser choices filter out helper executables and collapse each known slicer family to its latest discovered version, including stale recents left by older builds. Full paths are only tooltips. It then uses the native text dialog to name the button and saves that button's assignment. Later clicks launch directly; if a saved assignment is malformed or points to a missing slicer EXE, FlowCell clears that button assignment and prompts again. Regular panel buttons, panel fan popouts, and grouped script popouts all run through the same slicer assignment path and surface returned script status messages such as unsaved-blend blockers or launch cancellation. On the main page a successful script status (e.g. "Sent 1 model file to Slicer.") shows as a small green toast that fades out on its own after a couple of seconds (`.main-page__script-status`), separate from the red dismissable error box (`.main-page__script-error`) which is still used for actual failures; the fan and grouped-script popouts still show the dismissable box. Recent slicers (`flowcell.slicer.recentExecutables.v1`, max 8) are convenience choices only and are never auto-assigned, so multiple slicer buttons can point to different slicers. Deleting a slicer button through FlowCell clears that button's assignment. Assignment/recents/detected-installed-slicer handling lives in `FlowCellFrontend/src/lib/slicerLauncherAssignments.ts`, `FlowCellFrontend/src/lib/tauri.ts`, and `FlowCellFrontend/src-tauri/src/main.rs`; the existing Orca/Cura buttons still use their saved launcher paths.
- The legacy Organize Folder run (`Organize-FolderCore.ps1`) no longer writes `organize-folder.log.txt`; its full record (file moves, structure renames, recycled directories, duplicates, snapshots, conflicts, unresolved items, plus rollback data) is written to `organize-folder.undo.json`.
- Normal repository startup runs `flowcellbackend\helpers\Start-FlowCellPreflight.ps1` before reusing, building, or starting the frontend. Missing or failed preflight stops both normal and portable startup, core registration failures propagate instead of opening FlowCell with a broken program rail, and successful runs write a completion marker to `flowcellbackend\local\logs\startup-preflight.log`. Startup preflight repairs `flowcellbackend\local\bindings.ini` registrations for existing built-in program folders (Illustrator, Windows, Blender, and Photoshop), so a missing or damaged registry is repopulated from the folders on disk instead of coming back as Windows-only.
- `flowcellbackend\helpers\Start-FlowCellFrontend.ps1` decides whether to rebuild the Tauri frontend on launch by comparing the current source against two freshness files in `FlowCellFrontend\src-tauri\target\release` (`.flowcell_frontend_source_commit` = `git rev-parse HEAD`, `.flowcell_frontend_source_stamp` = a hash of source file sizes/mtimes); it writes those stamps only after its own `npm run tauri build`. A manual `npm run tauri build` therefore leaves the stamps stale and the next launch rebuilds again, so run `flowcellbackend\helpers\Update-FrontendBuildStamp.ps1` after a manual build to refresh the stamps (best-effort; on drift the only cost is one extra startup rebuild) so the next launch starts the existing binary without rebuilding. Reusing an already-running frontend now requires a visible real main Tauri window titled `FlowCell`; if the process is alive but only exposes internal windows such as the tiny Tao event target or tooltip handles, the launcher treats it as stale, stops it, and starts a fresh frontend instead of reporting a fake focus success.
- Layers Builder is a separate Illustrator layer/object manager that becomes the primary highlight-driven layer panel, leaving the original `Layers` panel fully intact as a fallback. It has three parts. (1) A warm-bridge JSX action `ill-layers` (`Programs/Illustrator/Illustrator Git Scripts/LayersBuilder/layers.jsx`) scans and mutates the document's layer/sublayer tree (scope: layers + sublayers only, no pageItems) and returns the fresh tree as JSON; layers are addressed by a dot-path "key" of layer indices (e.g. `0.2.1`) recomputed each scan. Supported ops: scan, create (top or sublayer), rename, delete (with `force` to temporarily unlock/unhide), duplicate, setlock, setvis, move. (2) The `Build Layers` window (`pages/build-layers/BuildLayersWindowPage.tsx`, window kind `build-layers`, opened via `openBuildLayersWindow`) is a frameless FlowCell window (decorations off — no native titlebar/min/max/close): hold Space and drag anywhere to move it, with edge/corner resize handles (`startResizeDragging`), like the toolbox windows. Its label `flowcell-build-layers` is listed in `FlowCellFrontend/src-tauri/capabilities/default.json` `windows` — required, or every `core:window:*` API (drag/resize/setSize) is silently denied for the window. Resizing uniformly scales the whole UI: the content is laid out at a canonical 360px width and a `transform: scale(windowWidth/360)` surface fills the window (the toolset surface-scale pattern). Each row has an Illustrator-style "target" circle on the far right; clicking it runs the `ill-layers` `select` op, which selects all artwork on that layer/sublayer in Illustrator (temporarily unlocking/unhiding) and makes it the active layer. Its content is chrome-light: just a toolbar (+ Layer, + Sublayer, Rename, Refresh, Duplicate, Delete, Force Delete) and the live tree (no title header, no bottom info bar; errors show as a thin red line only on failure). Click a row to select it as a FlowCell target, Ctrl/Cmd-click to toggle, Shift-click to select a contiguous range; selection is FlowCell-owned and independent of Illustrator's native panel, and locked/hidden rows are selectable. Each row has per-row lock/visibility toggles. The row whose key equals Illustrator's `doc.activeLayer` (returned by the scan as `active`) is shown bold — that is a fresh read of Illustrator's active layer on each scan, not a live subscription. Delete/Force Delete remove the highlighted layers directly by key (work on empty/locked/hidden layers). The tree scrollbar is visually hidden (`scrollbar-width:none` / `::-webkit-scrollbar{width:0}`) while still scrolling. The tree auto-refreshes after every FlowCell-initiated op, plus the manual Refresh button. It also re-scans when an Illustrator Layers / Layers Builder panel button runs: `runPanelScript` emits `flowcell:illustrator-layers-changed` (exported as `ILLUSTRATOR_LAYERS_CHANGED_EVENT`) and the window listens and re-scans twice (~350ms and ~1100ms, since the panel `.jsx` runs asynchronously in Illustrator after the click is accepted) — so e.g. clicking the `delete sublayer` panel button updates the window without a manual Refresh. Highlighted keys are persisted to `flowcellbackend/local/illustrator-layers-highlight.json` (and an OS-temp mirror) via the `set_illustrator_layers_highlight` Tauri command. The tree read/mutate path is the async `run_illustrator_layers_action` command (Tauri `async` + `spawn_blocking` so the possibly-multi-second cold-start PowerShell call never freezes the WebView), which invokes `Invoke-IllustratorFlowCellAction.ps1 -ActionId ill-layers -Wait` via `powershell -EncodedCommand` (base64 UTF-16LE — the only reliable way to pass the args JSON with embedded quotes through powershell.exe) and returns the bridge response JSON. The shared bridge client (`Invoke-IllustratorFlowCellAction.ps1`) sets pipe Read/Write timeouts best-effort because .NET Framework PipeStream does not support them (assigning them previously threw and broke every bridge call). (3) The `Layers Builder` panel (`Panels/Layers Builder/`, generated from the original `Layers` panel by `Programs/Illustrator/SupportScripts/New-IllustratorLayersBuilderPanel.ps1`) contains a self-contained `.jsx` copy of every original Layers button plus a `Build Layers.jsx` launcher (intercepted by `runPanelScript` to open the window). Most artwork-driven buttons get a selection prelude; structure-driven buttons listed in the generator's `$directBodies` map (currently `delete sublayer`) instead get a self-contained body that deletes/edits the highlighted layers directly by key (so they work on empty/locked/hidden layers, which the selection-driven originals cannot). Illustrator panels only run `.jsx`/`.js` and execute them inside Illustrator, so each generated button is a `.jsx`: the artwork prelude reads FlowCell's highlight set from the OS temp folder (`Folder.temp/flowcell-illustrator-layers-highlight.json`, written there as a mirror by `set_illustrator_layers_highlight`), resolves the highlighted layers to their real pageItems (temporarily unlocking/unhiding the layers and their ancestors), selects them, then the unchanged original Layers script body runs, and a `finally` block restores layer lock/visibility — so e.g. Snapshot works on highlighted locked/hidden layers. Re-run the generator after adding buttons to the original Layers panel to keep the two in sync. The tree action is registered in `Programs/Illustrator/illustrator-actions.json` (`ill-layers`).

- The main-page top-left action row has a Settings button to the right of Refresh. Layout snapshots store managed window bounds in Tauri's physical desktop pixels (Version 7 marks that format; loads take the saved pixels verbatim with no unit conversion or monitor guessing) and restore them position-first-then-size via `applyWindowPlacement` (windowing.ts) / `applyWindowBounds` (MainPage): applying size before position let a restored window transit a different-scale monitor, and Windows' WM_DPICHANGED rescale then multiplied the just-applied size by the DPI ratio — on a 100%/150%/175% mixed setup every saved toolset restored at exactly 2/3 size at the correct position — so the window is parked on its final monitor first and only then sized, which makes save/load a pixel-exact round trip on any monitor arrangement; Panel Fan's collapsed owner anchor is also persisted/restored in physical pixels, with its DOM-measured owner/expanded geometry scaled only at the native-window boundary, so a fan saved on a 175% monitor does not restore as a huge offscreen/cut-off logical window; single-button script popouts such as `update github` always restore and save with the canonical one-button size so an accidental tall captured window does not keep moving/resizing the button. - Place Picture persistence stays split from startup persistence: top Browse, bottom Browse, Place Picture, Grid, and Clear update only live/project Place Picture state, while only the `Startup` button writes the Place Picture entry of the global Blender startup-state file.
