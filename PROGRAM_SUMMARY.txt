FlowCell Program Summary
Last updated: 2026-08-05

When you are done making changes and they require a rebuild, you can stop the current running process and rebuild it as soon as you're done.

Purpose
-------
FlowCell is a Windows desktop command surface for program-specific script Buttons, editable skins and geometry, popouts/fans, program bridges, layouts, bindings, and local automation.

Current Architecture
--------------------
- The canonical Button system is the only Button runtime. It owns main-panel Buttons, tool-set children, popouts, fans, skins, geometry, editing, activation animations, and execution targets.
- `flowcellbackend/local/button-system/button-state.json` is canonical Button state.
- Program manifests and owned source packages replace program-specific script/button inventories in application core.
- Legacy program-script records and source comment directives are migration input only; `FlowCellFrontend/src-tauri/src/program_sources/migrate.rs` is their sole reader and preserves raw legacy Button metadata through an owned migration package.
- Keep this file structural and current. Detailed behavior belongs in the focused docs and implementation.

Repository Map
--------------
- `FlowCellFrontend/src/button/` owns the Button schema, host, renderer, surfaces, editor, skins, state, runtime dispatch, geometry, popouts, fans, activation animations, and Button windows; `FlowCellFrontend/src/assets/button-animations/` owns bundled transparent sprite assets.
- `FlowCellFrontend/src/pages/main/MainButtonHost.tsx` integrates canonical Buttons into the main window.
- `FlowCellFrontend/src-tauri/src/button_state.rs` owns revisioned, atomic Button-state commits and uninstall coordination.
- `FlowCellFrontend/src-tauri/src/program_sources/` owns program manifest loading, versioned bundled-source synchronization, source install/update, active records, execution, deletion, durable transactions, and one-time migration. Bundled-source adoption can upgrade migrated records whose owned package/source paths still use the old exact absolute spelling; the transaction accepts only the absolute paths that resolve to that owner's expected Local Scripts package and rewrites the committed record into the current relative form.
- `FlowCellFrontend/src-tauri/src/main.rs` is composition only. Focused owners under `FlowCellFrontend/src-tauri/src/commands/` handle managed program/panel setup, bindings and Tool Set Button hotkeys, macros, generic file/recycling services, execution bridges, windows/topmost, and layouts. Core owns no slicer code: `commands/slicers.rs`, the `load_slicer_executable`/`launch_slicer` commands, and the `programRails.ts` slicer-launch branch were removed. The Orca, Cura, and generic Slicer Blender packages each resolve their own executable (saved `runtime/<slicer>_launcher.json`, then a well-known install-path probe, then a native picker) and spawn it detached with the exported STL paths as arguments. Dedicated Orca and generic-Slicer-as-Orca first setup uses a native Yes/No/Cancel prompt for `Allow only one OrcaSlicer instance`, states the consequence of turning it off, reads and writes Orca's real checksummed `app.single_instance` preference through a backup plus atomic replacement, and refuses to edit the preference while Orca is running. No `requires_flowcell_*_launch` response contract remains.
- Setup Organization is a folder-tree editor. Its page has two panes: `Folders` is an Explorer-style tree the user adds to, renames, deletes, and can fill from any real folder via `Load tree from folder…` (read-only against the source, breadth-first, with an optional folder cap defaulting to 12); `Files` owns the selected folder's assignments — file-group checkboxes with per-group `edit` (add/remove that group's file types under its stable ID, so every profile referencing it follows) and inline creation, a direct extension field, a `Collect all other files here` catch-all toggle, an `Ignore this folder` toggle, and `Apply`, which commits the selection so returning to that folder shows it again. A folder row displays assigned groups by name, so a 39-extension group reads as `3D` rather than its extension list. Profiles are `flowcell.windows.setup-organization.profile.v3`: an ordered flat folder list where order is routing order, each entry carrying `groupIds`, `fileTypes`, `ignored`, and `catchAll`. At most one folder may be the catch-all and it may not also be ignored; both rules fail closed at save. Shared groups split into plain file groups (`Images`, `3D` - neutral/interchange formats only) and program file groups (`Blender`, `Illustrator`, `Fusion 360`), with no extension in two groups. A profile also carries `programFolders`: each entry binds a program file group to a root-level folder named after the group, created only when at least one matching file is present anywhere in the scan, and claiming that group file types ahead of every ordinary folder route. An entry may name another saved profile to build inside that folder; when that nested profile assigns the same program group to one of its own folders, that folder becomes the destination and overrides the program folder root. A profile cannot nest itself, cannot reference a non-program group, and cannot be deleted while another profile nests it. Ignored folders are still created - ignoring governs whether files move out, not whether the folder exists - so the shipped `Program Tree` profile (`02 snapshots`, `03 archive`, `04 trash`, all ignored) builds that structure inside any program folder it is attached to. Roles, program folders, snapshot/live versioning, root bindings, resolution modes, and runtime ambiguity prompts are gone; a profile that assigns one extension to two folders is rejected at save. Profile names are unique because the name becomes the installed Button's label, and deleting a profile still referenced by an installed Button fails closed.
- Installing a profile stages and installs an ordinary Windows Button labelled with the profile name and bound to that profile ID, so it works on first press with no prompt. Pressing it resolves a target folder from its argument or the clipboard, validates any existing project marker before mutation, creates missing active profile folders, scans recursively, moves each file to the first folder in profile order claiming its extension, never overwrites, leaves unmatched files and current ignored subtrees untouched, performs enabled Recycle Bin cleanup, writes an undo journal, and atomically rewrites the project marker.
- `.flowcell-project.json` is the cross-program project marker defined by `Programs/Windows/Windows Git Scripts/Files/Setup Organization/formats/project-marker.v1.schema.json`. A Setup Organization organizer Button fully validates and reads it before every run, then rewrites it with the current profile identity, lowercase-extension-to-relative-folder destination map, and logical ignored paths, including configured program/nested-profile paths even when that program route is inactive. When enabled, the previous marker's ignored paths are the only whole-tree cleanup candidates: a path is recycled without routing its contents only when the current profile no longer owns it. Missing markers produce no stale candidates, while invalid/unsafe markers, unsafe existing stale paths, and unresolved current program/nested-profile ownership fail closed before mutation. A failed stale-tree recycle leaves the previous marker in place so the next run retries it. The Blender bridge resolves the open `.blend`'s project root and its STL/PNG export folders from that marker so program Buttons follow whichever profile organized the project; the previous fixed `01 src/00 assets` layout remains only as the fallback for projects with no marker.
- `FlowCellFrontend/src/pages/installed-page/` and `FlowCellFrontend/src-tauri/src/program_sources/installed_page.rs` own the generic installed-page sandbox, message broker, schema/capability validation, owner state, and generated-Button authorization. Product page UI and actions live only in their installed program-owned packages.
- `flowcellbackend/` is the canonical AutoHotkey/PowerShell backend and launcher root.
- `flowcellbackend/local/` is ignored durable runtime state: bindings, Button state, layouts, logs, owner runtime state, program data, command payloads, and private configuration.
- `Programs/` contains manifest-defined program packages, tracked Git Scripts catalogs, ignored owned Local Scripts installs, active panel source records, and runner adapters.
- `docs/buttons.md` is the Button owner/file map. `docs/repository-layout.md`, `docs/flowcell-program-registry.md`, `docs/flowcell-toolset-manifest.md`, and `docs/blender-scripts.md` define source/package contracts.

Canonical Contracts
-------------------
- `button-state.json` owns Button records, placements, surfaces, skins, popouts, fans, per-Button activation animation assignments and physical bounds, and settings. No parallel Button state file is authoritative.
- Canonical Button-state reads are recovered, read-only snapshots. Main alone performs legacy migration and registered bundled-source synchronization once during startup, publishing only a changed authoritative revision; secondary windows subscribe before their initial pure load and never synchronize program sources as a render-time side effect. Main accepts documents monotonically by revision and refreshes the active panel's source list when its canonical source inventory changes, after the first accepted document, and after bootstrap completes so an earlier filesystem read cannot strand newly synchronized sources off-screen.
- Button-owned Local Scripts packages are the installed source of truth. Each source owner has `Programs/<Program>/<Program> Local Scripts/<ownerButtonId>/` plus `Programs/<Program>/Panels/<Panel>/<ownerButtonId>.flowcell-source.json`.
- `<Program> Git Scripts` is a tracked catalog only. Authorized source-install flows copy into the owned Local Scripts package; ordinary catalog edits do not modify installed Buttons. A program manifest may explicitly version and synchronize named `bundledSources`, preserving existing owner IDs and presentation.
- Source installation, update, and deletion use canonical package transactions. Main's existing Add Button flow opens the Button Editor locked to the chosen Program and Panel and automatically prompts once for source content; the Editor exposes no separate import, update, or delete controls. A raw file is a script; a selected package folder must contain exactly one root `flowcell.script.json` or `flowcell.toolset.json`, and selecting a manifest package's declared entry file promotes the whole package. Companion-file, dual-manifest, and manifest-free-folder imports fail closed. Updates preserve owner/placement IDs, presentation, dependent popout/fan references, and the owner's `runtime/` state. Tool-set slot removal/rename requires delete/re-add; an explicit append-only update policy may add deterministic missing children without replacing the surviving graph. Delete removes the complete owned Button graph, bindings, program runtime artifacts, active record, Local package, runtime state, and managed Pop, Fan, and page windows; window cleanup waits for in-flight opens and remains an idempotent post-commit effect. A durable pending-canonical journal reconciles an interrupted install against exact canonical/source identity on startup.
- The polished Buttons Editor has three panes: navigation and placement controls on the left, the complete Button workspace in the center, and the Skin Editor on the right. A fresh Editor window without usable supplied layout bounds maximizes before first show on the monitor selected by its initial placement, filling that monitor's available work area; an explicitly restored layout remains authoritative. Its restore-down baseline is `2093 x 1322` logical pixels. Program, Panel, Button, and Placement selectors resolve only exact existing Main, Pop, or saved legacy Fan occurrences while keeping every sibling Button visible; Placement contains no synthetic navigation actions, and every visible option is named exactly `Main Page`, `Fan`, or `Pop-out` while retaining its concrete surface identity behind the option. A tool-set child surface is a `Pop-out`. Every regular or Tool Set Pop-out exposes one `Fan` checkbox immediately above `Save Pop-out Settings`; checking it adds or reveals that Pop-out's exact owner Button on an expanded authoring board, while unchecking it retains and hides the owner placement. The Editor exposes no source/action library or legacy Fan-surface construction/membership controls and never fabricates a legacy Fan surface. `Save Main Page Settings`, `Save Fan Settings`, or `Save Pop-out Settings` opens a native file-save dialog and writes a strict `.flowcell-button-settings.json` v1 file under the matching `flowcellbackend/local/Button editor/Main Page`, `Fan`, or `Pop-out` folder. The file captures the selected surface's exact ordered Button membership and complete presentation: frame and uniform size; placement geometry, sizing, text, highlights, cycles, and visual maps; each effective literal skin; shared Button label, activation behavior, and activation animation; the Pop-out's Pop/Fan interaction mode and exact optional owner placement; and applicable container behavior. It excludes execution targets, action/source packages, live activation state, and application-managed desktop window layout. The same action performs the revision-safe scoped canonical commit, preserving concurrent external deletion and action identity; it is not the application-wide Save Layout operation. Every skin, assignment, Button Text, animation, and default write also keeps its requested scope frozen and retries against a freshly loaded canonical revision when another window commits first, so a normal `Button state changed before Save` race does not discard the Editor action or overwrite unrelated Pop/Fan changes. The existing Edit/Run switch remains in the left rail so the workspace can still execute Buttons and preview their activation behavior.
- The Editor's Program selector also exposes the synthetic `FlowCell Main Page` scope without passing it through registered-program panel lookup or source import. Its Panel selector divides non-deployable application controls into `Program Rail`, `Panel Rail`, `Button Section Rail`, and `Header Buttons`: each registered program has its own stable canonical Program Rail presentation; Panel Rail aliases the real per-program panel-owner Buttons individually; Button Section Rail excludes installed script Buttons; and Header Buttons includes Minimize, Maximize, and Close. Ordinary registered-program discovery may add or reconcile known controls but never deletes an absent program's presentation; program rename/removal preserves or removes the matching Main Page control only in the same canonical transaction. The Main Page remains authoritative for dynamic rail/header slots, adaptive header height, live count labels, and disabled state; each selected canonical control independently owns its skin, text, animation, authored size, and position, and the live Main Page consumes its saved placement coordinates.
- `Load Main Page Settings`, `Load Fan Settings`, or `Load Pop-out Settings` sits directly below its matching Save action and opens the corresponding type folder. A load must match the placement category and concrete surface subtype, every saved Button ID must still be canonically installed, and cross-surface reuse must also match the selected Program and Panel; a file tied to the same stable surface ID remains valid across Program/Panel renames. It replaces only the selected surface with the file's exact Button amount, order, frame, presentation, and container behavior as one undoable Editor draft; Buttons not listed are removed from that surface, saved Buttons are restored without importing or changing their execution targets, and `Save … Settings` remains the explicit canonical commit. Tool Set child membership stays package-owned, so its settings cannot add or remove actions. A Tool Set settings file may also serve as a presentation template for another installed Tool Set with the same child count: children map by declared slot and then saved order, while the target owner, actions, fields, labels, ownership, and activation behavior remain intact. Directly below Load are `Load … Default` and `Update … Default`. Each concrete surface owns one internal default under its type folder: the first visit lazily captures whatever that surface currently has in committed Button state, Load stages that snapshot, and Update atomically replaces it from the current Editor draft after a revision check.
- Main's `Save Layout` and `Load Layout` native pickers own `flowcellbackend/local/layouts/Main Page` as their default folder and use the Main-specific machine-local key `flowcell.main-page-layout-directory.v1` when remembering a deliberately chosen directory. The Main-page buttons are only the trigger: a strict current layout stores the exact open managed secondary-window set—Button Editor, Pop-out, Fan, and installed Page—with Pop/Fan semantic physical bounds and Editor/Page native physical bounds. Before closing anything, Load validates every bound and re-resolves every saved Page through its active installed descriptor; it then closes the current managed set, awaits every managed window's actual destruction before a stable label can be reused, and reopens the complete saved set through the existing window helpers. Stateful Button listener teardown observes Tauri's asynchronous unlisten result, retries once across a listener-table race, and contains final teardown failure so a closing host cannot trigger the global fatal screen. Editor/Page move and resize events retain their last usable native bounds so a minimized window is not omitted, while minimized-sentinel coordinates are rejected in layout files. Layout files never store or mutate Main-window bounds, Main navigation, Main Button placement, canonical Button/action state, or transient settings-preview windows. The picker folder remains separate from Button Editor Main Page, Fan, and Pop-out settings-file folders.
- `Animation` opens a dedicated page without reducing the existing activation-animation feature. Its selector includes `No animation` and every registered preset, and Apply either clears or assigns the selected animation through an animation-scoped canonical save that leaves unsaved placement geometry untouched. A top-right X exits the Animation page and closes any open setup presenter without clearing the assignment. The page retains the complete position-and-size setup flow, saved physical bounds, explicit setup close action, and runtime playback. `Plus Rise` setup renders only the static PNG at its true maximum animation size; app-managed invisible edge/corner resizing remains locked to the source's 283:295 ratio, and the shared Button record saves that semantic maximum-size rectangle in whole physical desktop pixels. Playback derives a separate larger cursor-ignored transparent travel canvas, then uses 61 linearly timed motion samples over 1.2 seconds to rise continuously from faint/small through opaque/full size before shrinking and fading out. Runtime requests from Main, Pop, Fan, and Editor use deterministic live-window coordinator election and are generation-scoped. Only the primary activation event triggers it; selection and paired release/hover events do not.
- Every real program panel has one source-free `panel-owner` Button on that program's main panel-rail surface. It is the actual main-page panel selector, including Utility, and panel/program folder lifecycle creates, renames, or removes it; generic Button deletion cannot remove it. Panel discovery during ordinary program navigation is read-only: it publishes the filesystem panel list immediately, uses a fallback panel control while canonical presentation loads, and never prunes or rewrites owners from a potentially stale discovery snapshot. Managed Add Program offers register-only, add-everything, and exact custom plans from the package manifest, with explicit panel/contribution selection, dependency closure, destination panels, host-EXE confirmation, and a reviewed effect list. Add Panel creates an empty panel or copies one validated external folder without modifying the source; it rejects links, traversal, and FlowCell-owned runtime artifacts, while an existing case-insensitive panel match is an idempotent reconcile.
- A panel owner's Main placement and each saved legacy Fan placement reuse that same Button identity while retaining placement-specific geometry and skin overrides. Existing saved Fans remain fully supported: Run preview uses the saved open, close, and pinned rules; the default starts on the real owner, hover opens and hover-out collapses, owner click pins, and the next pinned click collapses. Separately, each Pop-out in Fan mode owns one real placement-specific owner on the same authored surface; Edit shows it alongside the content, Pop mode hides it without deleting its geometry, and runtime collapses to that exact placement. Tool Set child/member arrays never absorb the owner.
- A fan setup's `collapsedPanelOwnerBounds` desktop anchor is optional: it is absent until the user space-drags the collapsed fan, which persists the visible semantic frame in real physical desktop pixels. The owner frame is derived from its applied visual envelope and effective WebView pixel ratio while preserving the owner's surface origin, so shadows and other overflow do not clip or shift the later expanded frame. Unanchored fans open centered over the launching window, and loading strips legacy `{left: 0, top: 0}` placeholder anchors.
- The main-page Fan button prioritizes an exact nonempty panel selection (single-script Buttons plus Tool Set owners), labels itself `Fan (N)`, creates/reuses that member-set Fan, and opens it. With no selection it retains the saved/default workflow: no saved setup creates a persisted generic Fan, one opens directly, and several show the saved-setup menu. `ensureFanSetup` is idempotent per member set.
- Panel/program rename preserves stable Button and presentation IDs while migrating canonical identities, active/install records, typed targets, source paths, catalog manifests, panels, fans, and popouts. Program rename uses one durable outer journal with exact previous/next bindings and canonical Button documents; atomic writes, case-only temporary moves, startup recovery, external-drift refusal, live backend reload, and token recovery keep the native and canonical sides on the same proved state.
- Add Program and Add Panel use durable native journals around registration, enabled-contribution state, filesystem publication, normal source installs, and canonical owner commits; startup finalizes only an exact canonical/source match and otherwise rolls back the proved transaction. Add Program holds one source-quarantine guard across its complete selected-source batch and calls the caller-locked installer, while standalone source operations acquire that same guard themselves, preserving serialization without recursively locking the non-reentrant guard. Program removal writes a strict durable journal containing the exact pre/post bindings, exact enabled-contribution registration file state, and expected canonical owner IDs before unregistering; after canonical/source recovery, startup restores both native pre-delete states when that exact owner set remains or finishes unregistration and recycles the enabled-registration file when the exact scoped owner set is absent, while partial owners or unrelated state drift fail closed. An Add Program rollback treats a planned source that never reached its active-record publish boundary as absent, so a prepared transaction can still restore bindings and enabled state, recycle its created panel, and clear its journal. Panel deletion likewise prepares a strict journal and an identity marker before canonical cleanup, then recycles only the marked immediate-child panel after the exact owners and active records are gone; startup cancels while the exact owners remain and finalizes after they are absent. Empty expected-owner sets are accepted only for a proved-empty canonical scope and authorize immediate recovery finalization because no canonical commit bit exists. The available program package is kept, and obsolete-window closing is best-effort after commit.
- User-facing deletions go to the Recycle Bin. Source transactions use recoverable JSON writes and durable quarantine journals; startup finishes committed cleanup or rolls back pre-commit work after interruption.
- `flowcell.program.json` defines program identity, explicit managed-setup Panels, folder roles, allowed source types, runner, native owner policy, shortcut profile, and optional versioned Button contributions. Add Program persists the exact enabled contribution set under `flowcellbackend/local/program-registration/<programId>.json`; synchronization considers only that registered/enabled set. Only `required` makes a contribution mandatory in Add Program, `installOnAdd` is a setup default, and `installIfMissing` is solely the repair policy for an already enabled contribution.
- `flowcell.script.json` describes a single-script catalog package and may contain a strict `page` declaration. `flowcell.toolset.json` describes one owner, child slots/payloads, optional tool-set layout/fields, and an optional package-owned `stateQuery` restricted to a declared child slot plus the read-only `status` action; page-enabled Buttons are script packages, not tool sets.
- An installed page is not another Button type or a product route. Its ordinary single-script owner receives the generic `open-installed-page` target, and every open/action re-resolves that exact active record and Button-owned package. Its managed native label includes a hash of the exact owner identity so sanitized or truncated owner names cannot collapse distinct Page windows. The page manifest declares only contained resources, strict request/response schemas, capabilities, owner-state format, optional shared program-data namespace, supported data formats, refresh events, window settings, and package config. Installed-page host styles stay class-scoped so their opaque page background cannot leak onto the global document roots used by transparent Pop/Fan windows.
- Installed page content runs in a raw WRY child WebView with no Tauri initialization scripts. The child reuses its parent Tauri WebView2 environment so opening a page does not cold-start a second browser/GPU process group or executable-local user-data folder; its controller remains InPrivate and isolated from Tauri globals. A package-only custom protocol serves sanitized entry HTML and declared resources under a deny-by-default CSP; native handlers block navigation, new windows, downloads, drag/drop, clipboard/browser features, and developer tools. Before any package script runs, a nonce-bound default-world raw-IPC proof must attest the isolated page URL, bridge globals, and absence of Tauri, Node, and privileged globals; Core fails closed until that proof passes. Closing a page first awaits raw-child unmount while its parent HWND is alive, then destroys the host and acknowledges its exact destroyed event, so WRY teardown never runs re-entrantly from parent destruction. The two-phase trusted broker validates installed identity, declared action/capability, and request/response schemas before and after any generic host capability. A page may call another installed program page only through a manifest-fixed provider handler: the caller must declare the exact capability published by the target action, the provider must be the active matching bundled page source, both request and response schemas are revalidated, and mismatched, ambiguous, or missing providers fail closed.
- Blender Theme, Save Blender, and Illustrator Layer Tree are ordinary page-enabled script packages owned by their program catalogs. Save Blender saves an already named `.blend` in place. For an untitled file, `Create new project` asks for a project name, remembered parent folder, and an optional canonical Setup Organization profile selected by human-readable name from the provider's profile list; UUID profile filenames remain internal, while Save Blender persists the stable profile ID. It creates `<parent>/<name>`, asks the Windows provider to prepare the real profile tree (including the planned Blender route), and saves `<name>.blend` in the returned Blender destination. `Add to existing project` keeps the editable Blender filename prompt and accepts any selected existing project folder: a valid marker's existing `.blend` route wins, otherwise its still-available saved profile may supply one Blender/static/catch-all destination, and an unassigned or unmarked folder simply receives the `.blend` at its root. This path creates only the one required destination path and never reruns organization, scans or moves project files, performs cleanup, creates unrelated profile folders, or rewrites the marker. Existing-project mode and its selected folder are deliberately not persisted. Later new-project saves reuse parent/profile settings, clear the name after success, and expose `Change Settings` to reopen the full form. Theme and Layer Tree keep their existing package-owned UI, assets, actions, configuration, helpers, adapters, and lifecycle behavior; Core contains only generic installed-page infrastructure.
- Windows Setup Organization is an ordinary Windows-owned page package. Its shared namespace under `flowcellbackend/local/program-data/windows/setup-organization/` owns V3 folder-tree profiles, reusable plain/program file groups, authenticated short-lived Button stages, and undo data; per-page preferences remain in the owner runtime. The page's literal `Install Button` action saves the active profile, stages an ordinary six-field script manifest, embeds the shared profile ID only in `organize_folder.ps1`, authenticates that stage, and installs or updates one stable package-derived Windows Button through the normal source transaction. Its provider-only `list-profiles` action exposes sorted profile IDs and human-readable names without storage paths, while `prepare-target` accepts an empty project root, canonical saved profile, and planned extension, runs the same organizer engine without a placeholder file, writes the genuine marker/tree, and returns the selected destination directory for program-owned consumers such as Save Blender. The separate `prepare-existing-target` provider accepts any safe existing project folder and never invokes that organizer engine: it uses an existing valid marker route when present, otherwise resolves one available saved-profile route, falls back to the selected folder when unassigned, and creates only that returned destination path without scanning, moving, recycling, journaling, or rewriting project content or metadata. Installed Windows page capabilities convert ownership-checked canonical `\\?\` paths back to ordinary DOS/UNC spelling before invoking Windows PowerShell 5.1, whose provider cannot resolve verbatim paths. The generated Button resolves the first nonempty copied-folder entry and otherwise falls back to a copied text path, applies its referenced shared profile, recycles the retired `organize-folder.profile.json` and `organize-folder.undo.json` artifacts after routing, and writes `.flowcell-project.json`. Two adjacent permanent per-profile switches can recycle empty folders absent from the current profile and, dependently, ignored folders recorded by the previous marker that the current profile no longer owns. Current static, program, nested-profile, and ignored paths remain protected; stale ignored-tree contents are skipped by routing and the whole stale tree goes to the Recycle Bin, ordinary cleanup preserves folders containing unmoved files, and every production removal uses the Recycle Bin. Deleting the Button removes its owner lifecycle while leaving the profile reusable.
- Numbered `bindings.ini` records have three target contracts. Existing single-script bindings remain path-based `ScriptPath` records registered and executed by the resident AutoHotkey backend even when the Tauri/frontend surface is closed. Tool-set owner and child bindings instead store `TargetKind=tool-set-owner|tool-set-child` plus canonical `ButtonId` and `OwnerButtonId`; only the running Tauri process registers their supported keyboard accelerators and refreshes them immediately after Binds changes. An owner hotkey press invokes the canonical managed-popout toggle directly, independent of Main's selection-only owner click, while a child press targets the active expanded owner and feeds the mounted child through its normal ButtonHost lifecycle. Binds keeps top-level navigation available but exposes children only for the selected Tool Set, and Current Panel Binds shows exactly that owner/child group. Illustrator additionally exposes one bind-only `Actions / Set Anchor` Core action backed by its shipped helper: its shortcut is stored under `ActionHotkeys`, registered pass-through only while Illustrator is foreground so the native Illustrator command still receives the same keystroke, and completes an immediate foreground automation call before returning so the keypress selection's visible-bounds box and center cannot be replaced by a later selection during process-launch delay. All native bindings mutations and source-removal rollbacks share one serialized document lane; hotkey synchronization reads its desired snapshot inside its own serialized lane, and legacy AutoHotkey binding edits preserve non-binding INI sections such as program registration and action hotkeys. A failed native registration rolls the binding change back, and no child payload or field snapshot is stored in the binding. Binds reads canonical Button state through a tolerant projection: optional canonical strings accept an explicit `null` exactly as they accept a missing key, and popout-unit ownership is modeled as optional because only `tool-set` units carry an owner while regular units are unowned and persist `"ownerButtonId": null`. Canonical data that Binds never consults therefore cannot abort the workspace load or a Tool Set shortcut save. Script binding targets are persisted in ordinary DOS/UNC spelling: ownership resolution rewrites installed source paths to verbatim `\\?\` form, but `bindings.ini` is executed by the resident AutoHotkey backend, and Windows PowerShell 5.1 cannot provider-resolve a verbatim path — `Join-Path` fails on one, so any script deriving paths from `$PSScriptRoot` dies before running. Binds strips the prefix both where it surfaces the target and where it writes `ScriptPath`, so an already-persisted verbatim path heals on the next rewrite.
- Page owner state is stored only at `<Program> Local Scripts/<ownerButtonId>/runtime/installed-page-state.json` in a strict envelope. Deleting a Theme or Layer Tree Button removes that state, its Local Scripts package, active record, bindings, canonical graph, registered runtime artifacts, and page window through the standard Button-deletion transaction; no product-specific Core state survives.
- Normal execution resolves only a valid `.flowcell-source.json` record whose installed source is inside its matching owner Local Scripts package.

Button Host And Skin Contract
-----------------------------
- The functional host owns interaction state, keyboard/pointer behavior, accessibility, validation, dispatch, and lifecycle.
- A placement may own one host-run activation cycle containing at least two ordered logical states; two states are the ordinary On/Off toggle, while any larger count is the same cycle model. State 1 is the initial session state. Each state owns one stable ID, label, `press`/`hover`/`release` advance trigger, one canonical latched resting visual supplied by the assigned skin, and optional partial-JSON `resultMatches`. Ordinary cycles advance locally and wrap to State 1. A result-mapped cycle instead waits for an authoritative action response; each newly opened expanded Tool Set resets its result-mapped placements to State 1, and later child responses set the exact index rather than guessing the next one. A declared package-owned read-only `stateQuery` is not run automatically during open/expansion. The host that receives an authoritative response applies it locally before broadcasting it to other mounted copies, so a Pop does not remain at State 1 merely because cross-window transport has no active Main coordinator. Real Hover, Pressed, Held, Play, and Release input temporarily renders its nonempty authored skin state, then settles back to the latched visual; an empty transient section falls through to the next authored input state or the configured resting visual, keeping a completed Hover target continuously applied instead of replaying its transition. Once an authored Pressed, Play, or Release presentation is requested, native window preparation must commit it to the skin before a fast pointer-up or action result may supersede it; finite motion then completes from the Web Animations completion signal before the newest requested appearance is applied. Functional Error and Disabled remain the highest-priority desired visuals without interrupting already-latched finite motion, and edit-focus selection does not replace a configured visual. The current index remains session-only and keyed by placement ID across mounted windows; response mappings and query declarations do not persist the live index or alter skin source. One press/release gesture can advance at most once even when another mounted copy advances in between; cancel is not release, and a real hover entry advances at most once until leave. - Fan is now an interaction mode saved inside every regular or Tool Set Pop-out, not another placement type. The Button Editor shows a `Fan` checkbox immediately above `Save Pop-out Settings`; enabling it adds or reveals one exact owner placement on the Pop-out surface and expands only the authoring board, while disabling it retains and hides that placement. The older prohibition on Fan construction in the Editor applies only to legacy standalone Fan surfaces and membership editing; existing legacy Fans remain supported.
- Pop-out Fan runtime begins on that exact owner, hover-opens, hover-out collapses while unpinned, lets owner click pin/unpin, and collapses on Escape. Expanded geometry holds the owner fixed in physical desktop space and derives the surface origin as `ownerOrigin - ownerPlacement.xy * contentScale * effectiveWebViewPixelRatio`; Pop mode filters the retained owner, and legacy collapsed Tool Sets keep their synthesized-owner fallback. The large authoring board uses tight hitbox window fitting, so unused board space stays transparent and inert.
- Empty-canvas drag in the Button Editor marquee-selects placements; plain selection replaces, while Shift, Ctrl, or Meta toggles every clicked or boxed Button into or out of the selection. Every selected placement has a crisp pointer-inert host outline that follows drag previews without extending a glow or badge beyond the actual rectangle, and the left rail shows the exact selected count and Button labels with the focused item marked as editing. Dragging any selected Button moves the full selection by one snapped, clamped, swept-collision-checked delta and one undo transaction without changing relative offsets, sizes, rows, gaps, order, or z-index; the Fan owner remains independently selectable and is excluded from content Re-order. `Align top-left Button to corner` rigidly changes only selected content `x/y` so its actual top-left Button reaches the surface corner while the Fan owner stays fixed. `Align to the Top Left button` keeps that anchor fixed and packs the same selected content rows and order to the current Button Sizing gap on both axes. Both fail atomically rather than moving the owner, unselected Buttons, or a Button to another row.
- Pop-out settings v1 remains backward-compatible: absent interaction/owner fields normalize to Pop with no owner. A Tool Set Pop-out settings file may be loaded into another installed Tool Set with the same child count; it maps children by declared slot and then saved order, preserves the target owner, actions, fields, labels, ownership, and activation behavior, and applies only saved layout/skin presentation and Pop/Fan behavior.

- Illustrator-scoped popouts temporarily detach their native owner while Windows taskbar previews are active, retain the real Illustrator owner through that preview, and restore it afterward so activating another program immediately returns the popout behind Illustrator.
- Program-scoped Pop, Fan, and installed-page windows use one native placement state machine. An explicitly opened Pop/Fan receives a post-show normal-band reveal tied to the opening FlowCell window and then to the revealed window itself. Only an exact manifest `processNames` match for the actual foreground process may select `TOPMOST`; transparent Pop/Fan windows otherwise remain in the normal band with geometry-selective input even when the owning program is closed or inactive, preventing visible controls from passing clicks to unrelated windows underneath. Opaque installed pages retain normal input and may continue in the normal band when focused. Installed pages use standard native chrome for dragging, minimizing, and closing. Taskbar previews still suppress input and demote every scoped window behind the real foreground HWND (or to the bottom as a fail-safe), while Illustrator's exact foreground match retains its owner-bound topmost behavior. Scoped-window IPC commands that share the native placement worker's apply lock execute off the main thread, preventing WebView focus callbacks from deadlocking against worker-dispatched Tauri window access.
- Layout restore and collapse/expand use saved physical-pixel managed-window bounds and canonical Button surface identities, preserving mixed-DPI size and owner anchors. Restore resolves its target program and panel before exposing either selection, then performs a request-scoped source refresh; whichever matching refresh wins also consumes the target-scoped saved Button selection, including an explicitly empty selection, instead of relying on unchanged React dependencies to reload cleared Buttons.
- Pop and Fan setups save a `surface`, `hitbox`, or `visual` window-fit mode. Their non-resizable transparent Tauri host is a large fixed canvas covering the active monitor work area (and any semantic frame outside it), starts cursor-ignored, and becomes cursor-active whenever the pointer is over a Button host, tool field, or Pop resize handle; after a Button receives pointer-down, the host stays cursor-active through pointer-up even if an authored animation moves the live core away. Owning-program state controls native topmost promotion, not whether a visible control can be clicked. Transparent gaps still pass clicks to the application underneath, and taskbar-preview suppression still disables the host. Hitbox/visual fits, hover/press/hold/play overflow, Fan expansion, and tool-set collapse/expansion move and resize only an absolutely positioned semantic content frame inside that canvas, preserving one invariant physical surface origin instead of repeatedly moving the HWND. The canvas grows or rehomes only when content would escape it, including monitor-edge drag/resize and mixed-DPI transitions. An unsized Pop starts at one design pixel per WebView CSS pixel; restored physical bounds use the destination WebView's effective pixel ratio, and scaled skin measurement retains skin-root and animated shadow/outline scale while normalizing ancestor content scale into design units. Hold Space and drag any visible Button to move the semantic frame; an expanded tool set stays expanded throughout that drag and persists the expanded placement. Pop corner handles track the visible Button/tool-field envelope even when that content is inset inside a larger saved surface, while resizing still scales and persists the complete semantic surface, preserves aspect, and anchors the opposite visible grip across mixed-DPI canvas changes. On release, real physical-pixel Pop/Fan bounds and semantic layout snapshots persist, while transient active envelopes and the large native canvas bounds never do.- One shared native input worker samples cursor and modifier state and emits only changed snapshots; each Pop/Fan reacts to those changes plus local geometry/DOM invalidation instead of polling native input every frame. Scope and input listeners subscribe before querying their initial state, retry transient setup/read failures, and fail closed to cursor-ignored; the serialized native cursor-style controller also retries a failed `setIgnoreCursorEvents` call and converges to the newest requested state. Newly created transparent windows initialize cursor-ignore fail-closed, while reopening an existing window leaves its live hitbox controller in sole ownership of that flag; Pop/Fan hitboxes start only after final canvas placement completes. Physical semantic bounds and cursor snapshots are mapped through the WebView's effective pixel ratio (including WebView zoom, with native DPI as fallback), so fixed-canvas placement and synthetic hover stay aligned. The window rejects pointers outside its semantic frame before consulting cached interactive membership, but reads exact viewport rectangles live after position-only frame movement, and it bypasses the render barrier for unchanged envelopes. Active visual overflow is measured only while the authored subtree has running motion plus final settle frames, so finite hover/play transitions stop consuming animation-frame work without changing skin source or hitbox ownership.

Validation
----------
- Frontend/Tauri changes: run the relevant frontend build; use `flowcellbackend/helpers/Start-FlowCellFrontend.ps1` with `-ForceRestart` when the running frontend must refresh.
- Rust changes: run `cargo check` plus focused tests.
- AutoHotkey changes: validate with AutoHotkey v2 and restart the hidden backend.
- PowerShell changes: parse-check touched scripts and run the narrow behavior test when practical.
- Blender source/bridge changes: compile-check Python where applicable and verify after add-on reload or Blender restart.
- Documentation-only changes: validate headings, links/paths, and stale-term removal; no application build is required.
- Portable program ZIPs contain only Git-tracked package files, require a tracked program manifest, and reject manifest-declared mutable folders, reparse points, containment escapes, and unsafe archive members; the Core ZIP contains no `Programs/` payload.
