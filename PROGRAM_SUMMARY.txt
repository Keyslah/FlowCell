FlowCell Program Summary
Last updated: 2026-07-23

Purpose
-------
FlowCell is a Windows desktop command surface for program-specific script Buttons, editable skins and geometry, popouts/fans, program bridges, layouts, bindings, and local automation.

Current Architecture
--------------------
- The canonical Button system is the only Button runtime. It owns main-panel Buttons, tool-set children, popouts, fans, skins, geometry, editing, activation animations, and execution targets.
- `flowcellbackend/local/button-system/button-state.json` is canonical Button state.
- Program manifests and owned source packages replace program-specific script/button inventories in application core.
- Legacy program-script records and source comment directives are migration input only; `FlowCellFrontend/src-tauri/src/program_sources/migrate.rs` is their sole reader and preserves raw legacy Button metadata through an owned migration package.
- Keep this file structural and current. Detailed behavior belongs in the focused docs and implementation.

Repository Map
--------------
- `FlowCellFrontend/src/button/` owns the Button schema, host, renderer, surfaces, editor, skins, state, runtime dispatch, geometry, popouts, fans, activation animations, and Button windows; `FlowCellFrontend/src/assets/button-animations/` owns bundled transparent sprite assets.
- `FlowCellFrontend/src/pages/main/MainButtonHost.tsx` integrates canonical Buttons into the main window.
- `FlowCellFrontend/src-tauri/src/button_state.rs` owns revisioned, atomic Button-state commits and uninstall coordination.
- `FlowCellFrontend/src-tauri/src/program_sources/` owns program manifest loading, versioned bundled-source synchronization, source install/update, active records, execution, deletion, durable transactions, and one-time migration.
- `FlowCellFrontend/src-tauri/src/main.rs` is composition only. Focused owners under `FlowCellFrontend/src-tauri/src/commands/` handle managed program/panel setup, bindings and Tool Set Button hotkeys, macros, generic file/recycling services, execution bridges, windows/topmost, layouts, and slicers.
- `FlowCellFrontend/src/pages/installed-page/` and `FlowCellFrontend/src-tauri/src/program_sources/installed_page.rs` own the generic installed-page sandbox, message broker, schema/capability validation, owner state, and generated-Button authorization. Product page UI and actions live only in their installed program-owned packages.
- `flowcellbackend/` is the canonical AutoHotkey/PowerShell backend and launcher root.
- `flowcellbackend/local/` is ignored durable runtime state: bindings, Button state, layouts, logs, owner runtime state, program data, command payloads, and private configuration.
- `Programs/` contains manifest-defined program packages, tracked Git Scripts catalogs, ignored owned Local Scripts installs, active panel source records, and runner adapters.
- `docs/buttons.md` is the Button owner/file map. `docs/repository-layout.md`, `docs/flowcell-program-registry.md`, `docs/flowcell-toolset-manifest.md`, and `docs/blender-scripts.md` define source/package contracts.

Canonical Contracts
-------------------
- `button-state.json` owns Button records, placements, surfaces, skins, popouts, fans, per-Button activation animation assignments and physical bounds, and settings. No parallel Button state file is authoritative.
- Canonical Button-state reads are recovered, read-only snapshots. Main alone performs legacy migration and registered bundled-source synchronization once during startup, publishing only a changed authoritative revision; secondary windows subscribe before their initial pure load and never synchronize program sources as a render-time side effect. Main accepts documents monotonically by revision and refreshes the active panel's source list when its canonical source inventory changes, after the first accepted document, and after bootstrap completes so an earlier filesystem read cannot strand newly synchronized sources off-screen.
- Button-owned Local Scripts packages are the installed source of truth. Each source owner has `Programs/<Program>/<Program> Local Scripts/<ownerButtonId>/` plus `Programs/<Program>/Panels/<Panel>/<ownerButtonId>.flowcell-source.json`.
- `<Program> Git Scripts` is a tracked catalog only. Authorized source-install flows copy into the owned Local Scripts package; ordinary catalog edits do not modify installed Buttons. A program manifest may explicitly version and synchronize named `bundledSources`, preserving existing owner IDs and presentation.
- Source installation, update, and deletion use canonical package transactions. Main's existing Add Button flow opens the Button Editor locked to the chosen Program and Panel and automatically prompts once for source content; the Editor exposes no separate import, update, or delete controls. A raw file is a script; a selected package folder must contain exactly one root `flowcell.script.json` or `flowcell.toolset.json`, and selecting a manifest package's declared entry file promotes the whole package. Companion-file, dual-manifest, and manifest-free-folder imports fail closed. Updates preserve owner/placement IDs, presentation, dependent popout/fan references, and the owner's `runtime/` state. Tool-set slot removal/rename requires delete/re-add; an explicit append-only update policy may add deterministic missing children without replacing the surviving graph. Delete removes the complete owned Button graph, bindings, program runtime artifacts, active record, Local package, runtime state, and managed Pop, Fan, and page windows; window cleanup waits for in-flight opens and remains an idempotent post-commit effect. A durable pending-canonical journal reconciles an interrupted install against exact canonical/source identity on startup.
- The polished Buttons Editor has three panes: navigation and placement controls on the left, the complete Button workspace in the center, and the Skin Editor on the right. Program, Panel, Button, and Placement selectors resolve only exact existing Main, Pop, or saved Fan occurrences while keeping every sibling Button visible; Placement contains no synthetic navigation actions, and every visible option is named exactly `Main Page`, `Fan`, or `Pop-out` while retaining its concrete surface identity behind the option. A tool-set child surface is a `Pop-out`. The Editor exposes no source/action library or Fan construction or membership controls and never fabricates a default Fan placement. `Save Main Page Settings`, `Save Fan Settings`, or `Save Pop-out Settings` opens a native file-save dialog and writes a strict `.flowcell-button-settings.json` v1 file under the matching `flowcellbackend/local/Button editor/Main Page`, `Fan`, or `Pop-out` folder. The file captures the selected surface's exact ordered Button membership and complete presentation: frame and uniform size; placement geometry, sizing, text, highlights, cycles, and visual maps; each effective literal skin; shared Button label, activation behavior, and activation animation; and applicable Pop/Fan container behavior. It excludes execution targets, action/source packages, live activation state, and application-managed desktop window layout. The same action performs the revision-safe scoped canonical commit, preserving concurrent external deletion and action identity; it is not the application-wide Save Layout operation. Every skin, assignment, Button Text, animation, and default write also keeps its requested scope frozen and retries against a freshly loaded canonical revision when another window commits first, so a normal `Button state changed before Save` race does not discard the Editor action or overwrite unrelated Pop/Fan changes. The existing Edit/Run switch remains in the left rail so the workspace can still execute Buttons and preview their activation behavior.
- `Load Main Page Settings`, `Load Fan Settings`, or `Load Pop-out Settings` sits directly below its matching Save action and opens the corresponding type folder. A load must match the placement category and concrete surface subtype, every saved Button ID must still be canonically installed, and cross-surface reuse must also match the selected Program and Panel; a file tied to the same stable surface ID remains valid across Program/Panel renames. It replaces only the selected surface with the file's exact Button amount, order, frame, presentation, and container behavior as one undoable Editor draft; Buttons not listed are removed from that surface, saved Buttons are restored without importing or changing their execution targets, and `Save … Settings` remains the explicit canonical commit. Tool-set child membership stays package-owned, so a tool-set settings file may reorder or restyle its current children but cannot add or remove actions. Directly below Load are `Load … Default` and `Update … Default`. Each concrete surface owns one internal default under its type folder: the first visit lazily captures whatever that surface currently has in committed Button state, Load stages that snapshot, and Update atomically replaces it from the current Editor draft after a revision check.
- `Animation` opens a dedicated page without reducing the existing activation-animation feature. Its selector includes `No animation` and every registered preset, and Apply either clears or assigns the selected animation through an animation-scoped canonical save that leaves unsaved placement geometry untouched. A top-right X exits the Animation page and closes any open setup presenter without clearing the assignment. The page retains the complete position-and-size setup flow, saved physical bounds, explicit setup close action, and runtime playback. `Plus Rise` setup renders only the static PNG at its true maximum animation size; app-managed invisible edge/corner resizing remains locked to the source's 283:295 ratio, and the shared Button record saves that semantic maximum-size rectangle in whole physical desktop pixels. Playback derives a separate larger cursor-ignored transparent travel canvas, then uses 61 linearly timed motion samples over 1.2 seconds to rise continuously from faint/small through opaque/full size before shrinking and fading out. Runtime requests from Main, Pop, Fan, and Editor use deterministic live-window coordinator election and are generation-scoped. Only the primary activation event triggers it; selection and paired release/hover events do not.
- Every real program panel has one source-free `panel-owner` Button on that program's main panel-rail surface. It is the actual main-page panel selector, including Utility, and panel/program folder lifecycle creates, renames, or removes it; generic Button deletion cannot remove it. Panel discovery during ordinary program navigation is read-only: it publishes the filesystem panel list immediately, uses a fallback panel control while canonical presentation loads, and never prunes or rewrites owners from a potentially stale discovery snapshot. Managed Add Program offers register-only, add-everything, and exact custom plans from the package manifest, with explicit panel/contribution selection, dependency closure, destination panels, host-EXE confirmation, and a reviewed effect list. Add Panel creates an empty panel or copies one validated external folder without modifying the source; it rejects links, traversal, and FlowCell-owned runtime artifacts, while an existing case-insensitive panel match is an idempotent reconcile.
- A panel owner's Main placement and each saved Fan placement reuse that same Button identity while retaining placement-specific geometry and skin overrides. Existing saved Fans remain fully supported: Run preview uses the saved open, close, and pinned rules; the default starts on the real owner, hover opens and hover-out collapses, owner click pins, and the next pinned click collapses. Edit mode exposes the complete saved grid, but the Editor never creates a Fan or changes its membership.
- A fan setup's `collapsedPanelOwnerBounds` desktop anchor is optional: it is absent until the user space-drags the collapsed fan, which persists the visible semantic frame in real physical desktop pixels. The owner frame is derived from its applied visual envelope and effective WebView pixel ratio while preserving the owner's surface origin, so shadows and other overflow do not clip or shift the later expanded frame. Unanchored fans open centered over the launching window, and loading strips legacy `{left: 0, top: 0}` placeholder anchors.
- The main-page Fan button prioritizes an exact nonempty panel selection (single-script Buttons plus Tool Set owners), labels itself `Fan (N)`, creates/reuses that member-set Fan, and opens it. With no selection it retains the saved/default workflow: no saved setup creates a persisted generic Fan, one opens directly, and several show the saved-setup menu. `ensureFanSetup` is idempotent per member set.
- Panel/program rename preserves stable Button and presentation IDs while migrating canonical identities, active/install records, typed targets, source paths, catalog manifests, panels, fans, and popouts. Program rename uses one durable outer journal with exact previous/next bindings and canonical Button documents; atomic writes, case-only temporary moves, startup recovery, external-drift refusal, live backend reload, and token recovery keep the native and canonical sides on the same proved state.
- Add Program and Add Panel use durable native journals around registration, enabled-contribution state, filesystem publication, normal source installs, and canonical owner commits; startup finalizes only an exact canonical/source match and otherwise rolls back the proved transaction. Add Program holds one source-quarantine guard across its complete selected-source batch and calls the caller-locked installer, while standalone source operations acquire that same guard themselves, preserving serialization without recursively locking the non-reentrant guard. Program removal writes a strict durable journal containing the exact pre/post bindings, exact enabled-contribution registration file state, and expected canonical owner IDs before unregistering; after canonical/source recovery, startup restores both native pre-delete states when that exact owner set remains or finishes unregistration and recycles the enabled-registration file when the exact scoped owner set is absent, while partial owners or unrelated state drift fail closed. An Add Program rollback treats a planned source that never reached its active-record publish boundary as absent, so a prepared transaction can still restore bindings and enabled state, recycle its created panel, and clear its journal. Panel deletion likewise prepares a strict journal and an identity marker before canonical cleanup, then recycles only the marked immediate-child panel after the exact owners and active records are gone; startup cancels while the exact owners remain and finalizes after they are absent. Empty expected-owner sets are accepted only for a proved-empty canonical scope and authorize immediate recovery finalization because no canonical commit bit exists. The available program package is kept, and obsolete-window closing is best-effort after commit.
- User-facing deletions go to the Recycle Bin. Source transactions use recoverable JSON writes and durable quarantine journals; startup finishes committed cleanup or rolls back pre-commit work after interruption.
- `flowcell.program.json` defines program identity, explicit managed-setup Panels, folder roles, allowed source types, runner, native owner policy, shortcut profile, and optional versioned Button contributions. Add Program persists the exact enabled contribution set under `flowcellbackend/local/program-registration/<programId>.json`; synchronization considers only that registered/enabled set. Only `required` makes a contribution mandatory in Add Program, `installOnAdd` is a setup default, and `installIfMissing` is solely the repair policy for an already enabled contribution.
- `flowcell.script.json` describes a single-script catalog package and may contain a strict `page` declaration. `flowcell.toolset.json` describes one owner, child slots/payloads, optional tool-set layout/fields, and an optional package-owned `stateQuery` restricted to a declared child slot plus the read-only `status` action; page-enabled Buttons are script packages, not tool sets.
- An installed page is not another Button type or a product route. Its ordinary single-script owner receives the generic `open-installed-page` target, and every open/action re-resolves that exact active record and Button-owned package. The page manifest declares only contained resources, strict request/response schemas, capabilities, owner-state format, optional shared program-data namespace, supported data formats, refresh events, window settings, and package config. Installed-page host styles stay class-scoped so their opaque page background cannot leak onto the global document roots used by transparent Pop/Fan windows.
- Installed page content runs in a raw WRY child WebView with no Tauri initialization scripts. A package-only custom protocol serves sanitized entry HTML and declared resources under a deny-by-default CSP; native handlers block navigation, new windows, downloads, drag/drop, clipboard/browser features, and developer tools. Before any package script runs, a nonce-bound default-world raw-IPC proof must attest the isolated page URL, bridge globals, and absence of Tauri, Node, and privileged globals; Core fails closed until that proof passes. Closing a page first awaits raw-child unmount while its parent HWND is alive, then destroys the host and acknowledges its exact destroyed event, so WRY teardown never runs re-entrantly from parent destruction. The two-phase trusted broker validates installed identity, declared action/capability, and request/response schemas before and after any generic host capability.
- Blender Theme and Illustrator Layer Tree are ordinary page-enabled script packages owned by `Programs/Blender` and `Programs/Illustrator`. Their UI, assets, action declarations, configuration, helpers, program adapters, and behavior ship inside those packages; Core has no Theme or Layer Tree component, renderer, route, identifier, dispatch branch, bundled registration, or fallback execution path. Theme keeps its long form scroll-accessible while hiding the page-owned scrollbar, and its Browse action selects a fresh image through the generic file service before asking the generic palette service to sample it. Theme opts into the generic Blender custom-action lifecycle: the package registers/unregisters its own restore handlers, timers, modal overlays, and owner-sidecar startup state, while generic deletion requires a running-Blender cleanup acknowledgement or performs offline sidecar recycling. Saved Theme packages in `flowcellbackend/local/blender_themes/` are explicit shared Blender program data and survive launcher deletion.
- Windows Setup Organization is an ordinary Windows-owned page package. It stores profiles only in `flowcellbackend/local/program-data/windows/setup-organization/`, keeps per-page preferences in its owner runtime, and creates profile Buttons through authenticated short-lived stages plus the normal Add Button transaction. Generated Button deletion removes its complete owner lifecycle while the explicitly shared profile remains reusable.
- Numbered `bindings.ini` records have three target contracts. Existing single-script bindings remain path-based `ScriptPath` records registered and executed by the resident AutoHotkey backend even when the Tauri/frontend surface is closed. Tool-set owner and child bindings instead store `TargetKind=tool-set-owner|tool-set-child` plus canonical `ButtonId` and `OwnerButtonId`; only the running Tauri process registers their supported keyboard accelerators and refreshes them immediately after Binds changes. An owner hotkey press invokes the canonical managed-popout toggle directly, independent of Main's selection-only owner click, while a child press targets the active expanded owner and feeds the mounted child through its normal ButtonHost lifecycle. Binds keeps top-level navigation available but exposes children only for the selected Tool Set, and Current Panel Binds shows exactly that owner/child group. Illustrator additionally exposes one bind-only `Actions / Set Anchor` Core action backed by its shipped helper: its shortcut is stored under `ActionHotkeys`, registered pass-through only while Illustrator is foreground so the native Illustrator command still receives the same keystroke, and completes an immediate foreground automation call before returning so the keypress selection's visible-bounds box and center cannot be replaced by a later selection during process-launch delay. All native bindings mutations and source-removal rollbacks share one serialized document lane; hotkey synchronization reads its desired snapshot inside its own serialized lane, and legacy AutoHotkey binding edits preserve non-binding INI sections such as program registration and action hotkeys. A failed native registration rolls the binding change back, and no child payload or field snapshot is stored in the binding.
- Page owner state is stored only at `<Program> Local Scripts/<ownerButtonId>/runtime/installed-page-state.json` in a strict envelope. Deleting a Theme or Layer Tree Button removes that state, its Local Scripts package, active record, bindings, canonical graph, registered runtime artifacts, and page window through the standard Button-deletion transaction; no product-specific Core state survives.
- Normal execution resolves only a valid `.flowcell-source.json` record whose installed source is inside its matching owner Local Scripts package.

Button Host And Skin Contract
-----------------------------
- The functional host owns interaction state, keyboard/pointer behavior, accessibility, validation, dispatch, and lifecycle.
- A placement may own one host-run activation cycle containing at least two ordered logical states; two states are the ordinary On/Off toggle, while any larger count is the same cycle model. State 1 is the initial session state. Each state owns one stable ID, label, `press`/`hover`/`release` advance trigger, one canonical latched resting visual supplied by the assigned skin, and optional partial-JSON `resultMatches`. Ordinary cycles advance locally and wrap to State 1. A result-mapped cycle instead waits for an authoritative action response; each newly opened expanded Tool Set resets its result-mapped placements to State 1, and later child responses set the exact index rather than guessing the next one. A declared package-owned read-only `stateQuery` is not run automatically during open/expansion. The host that receives an authoritative response applies it locally before broadcasting it to other mounted copies, so a Pop does not remain at State 1 merely because cross-window transport has no active Main coordinator. Real Hover, Pressed, Held, Play, and Release input temporarily renders its nonempty authored skin state, then settles back to the latched visual; an empty transient section falls through to the next authored input state or the configured resting visual, keeping a completed Hover target continuously applied instead of replaying its transition. Once an authored Pressed, Play, or Release presentation is requested, native window preparation must commit it to the skin before a fast pointer-up or action result may supersede it; finite motion then completes from the Web Animations completion signal before the newest requested appearance is applied. Functional Error and Disabled remain the highest-priority desired visuals without interrupting already-latched finite motion, and edit-focus selection does not replace a configured visual. The current index remains session-only and keyed by placement ID across mounted windows; response mappings and query declarations do not persist the live index or alter skin source. One press/release gesture can advance at most once even when another mounted copy advances in between; cancel is not release, and a real hover entry advances at most once until leave. Main's selection-only script Buttons may advance a Hover state on real entry, keep ordinary single selection clicks inert, and synthesize one Press/Release gesture only after successful double-click execution.
- The Skin Editor's `Button States & Behavior` section exposes a placement-only `Highlight on hover` checkbox plus a state count from 2 through 64, one Advance on dropdown per state, then a State and skin-dependent Visual state dropdown with an immediate real renderer preview. A result-mapped state adds one compact `Action: value` line whose tooltip shows its complete response matches. The highlight defaults off and applies a small host brightness lift to only that hovered placement without editing skin source or changing `[data-core]` measurement or hit testing. The visual list contains Base plus canonical sections authored by the active working skin; choosing one changes only that placement cycle and never rewrites skin code. Button Text uses those exact logical states for per-state labels and previews the selected state's assigned visual immediately. Save Settings persists the highlight and cycle. Button Text's bottom `Apply All` remains text-only and requires changed cycle IDs to be saved first. With a configured cycle it saves only placement-state labels and preserves the shared base Button label; without one it saves the base label and mirrors it into legacy activation-state labels so the compatibility runtime and preview agree. Legacy Button-owned activation behavior remains readable only as compatibility fallback for placements without a configured activation cycle.
- Main's Button section separates selection from execution: one ordinary click toggles that exact script, macro, or Tool Set owner in the current multi-selection, latching the skin's authored pressed state with no host outline unless that placement owns a cycle whose selected visual remains authoritative, while a double-click runs that Button's primary action directly on Main. Main suppresses the Button's authored hover/press/click actions and activation effect for the ordinary selection gesture, including Buttons whose `pressDown` event normally owns execution. `Fan (N)` retains selection-driven Fan creation/opening. `Open Pop`, immediately left of `Pop`, opens a native picker in the Pop-out settings folder and opens the selected regular or Tool Set settings file as an isolated temporary draft window; it does not load into an Editor surface, mutate or commit canonical Button state, or participate in Save Layout. Main remembers only `{ path, choiceId }` in machine-local storage under the stable panel-owner Button ID. `Pop` reloads and opens that panel's last-used file independent of Main selection, or directs the user to Open Pop when none exists. Once popped out, an ordinary click runs the Button through its normal runtime host.
- Skins are render-only and isolated. They cannot execute actions, mutate state, own bindings, or define source targets.
- Every skin contains exactly one measurable `[data-core]` and zero or one `{{label}}` token inside it. Textless and animation-only skins receive no synthesized text or fallback face; the saved Button label still supplies the accessible name.
- A skin that supplies a complete alternate appearance for a logical Button state is authored as one paste-ready composite: every alternate face is a pointer-inert nested visual inside that one stable `[data-core]`, and state declarations or CSS custom properties reveal the intended face. A skin may never embed another functional Button, another `[data-core]`, another hitbox, or a runtime skin swap for an alternate state.
- Skin authoring uses a neutral render-only core whose resting body matches the intended clickable footprint. Browser controls are forbidden inside skin markup. Newly authored packed skins may not invent transparent layout gutters, while literal conversions preserve the source control's complete visual box model, including authored padding or transparent depth space that positions its face/base/press travel; only outer demo/page spacing is removed. Inherited source typography is frozen to its resolved pixel font size/line height so natural geometry stays identical across Editor/Main/Pop/Fan. Pseudo-elements become equivalent pointer-inert real layers, absent source states stay empty, and a color-only request changes no geometry or unmentioned visual value.
- The compiler lifts the core's inline `style` into a lowest-priority `[data-core]` rule so ordinary state declarations override that core; nested visuals remain literal and consume custom properties initialized in Base. Skin paste headers tolerate whitespace and case.
- New skins, conversions, and complete replacements include every canonical paste header, including empty sections that clear stale keyframes or state. The repo-local `skin-author` preflight compiles the current parser/validator, requires the full replacement header set, requires an effective pixel font size and pixel line-height for labeled or `em`-sized cores, and rejects inherited core metrics or any semantic diagnostic before a paste block is returned. Original skins require a painted-footprint check; conversions require source/result rest-and-state geometry comparison because static validation cannot infer visual equivalence.
- The Skin Editor's Button Size section keeps width, height, and sizing behavior in a working preview until `Assign Size` or `Assign Size to Panel` is pressed. Responsive constrains `[data-core]` to the exact independent host width and height, aligns its authored resting offset to the placement origin, and skips root scaling so a responsive skin can reflow without geometric stretching. Proportional scales the complete authored root uniformly, derives the working ratio from the measured natural core, and aspect-locks numeric or canvas resizing. Stretch performs explicit independent X/Y root scaling and may distort typography, corners, and effects. `Assign Size` applies the target only to the focused placement; `Assign Size to Panel` applies it once to every Button next to that placement on its current surface, whether the occurrence is on Main, Pop, Fan, or another Button surface, and atomically compacts that same surface if it fits. Responsive and Stretch use the exact target dimensions; Proportional preserves each target Button's measured natural aspect when available and otherwise its current aspect. Both actions disable later label-driven geometry growth, neither enables or writes the separate legacy `Same size Buttons` surface format, and neither changes authored skin source. The size preview uses the isolated working skin, so unassigned skin edits still require their own Assign Skin action.
- After optional label injection and host scaling, the transformed `[data-core]` defines the Button's resting and accessible geometry and is the only node with Button interaction listeners. The placement-owned shadow host stays browser-reachable so its core can receive events but performs no activation from unused placement gutters; transparent Pop/Fan native gating discovers that host and tests the live core rectangle, so those gutters and decorative overflow remain click-through. Normal Edit drag and resize sample the complete pointer path and stop at the furthest valid edge without reflowing the workspace with collision warnings. The separate undoable Reorder mode pulls the grabbed Button out of reflow so it follows the pointer at animation-frame speed, infers exact visual row membership, exposes every insertion slot in every row plus explicit new-row boundaries, and uses lane-scoped, slot-bounded hysteresis so thin rows and between-row targets cannot be skipped. It closes horizontal gaps within each unchanged row, smoothly moves neighboring Buttons out of the way, and normalizes saved placement z-index. A Button never moves to another row unless it is the one being reordered, and an over-wide row fails atomically instead of rebalancing. `Snap to top left corner` left-packs each existing row and stacks those same rows upward from the surface origin without changing row count, row membership, or Button sizes. The left rail's `Same size Buttons` checkbox persists one authoritative surface size, atomically applies it to every member, switches them to fixed host sizing with label growth disabled, and compacts them at zero gap. Canvas resizing while linked updates every member atomically; delayed skin/text measurements cannot split the sizes. Unchecking stops future linked resizing while preserving the current fixed layout. No compatibility rectangle is overlaid and authored skin source is never rewritten for sizing.
- Reorder mode keeps the Button workspace unobstructed by omitting its persistent instruction banner; the overlay appears only when there is an actual blocked-reorder reason. Enabling `Same size Buttons` resizes and zero-gap packs Buttons within their existing visual rows and fails atomically rather than moving a Button into another row.
- Button Text wrapping is host-owned: `Shrink` keeps the injected label on one unbroken row, while only `Stack whole words` and `Shrink and stack` may create multiple whole-word rows. Text fit measures the host-injected label glyphs against the constrained core instead of treating the skin's full padded/scroll box as text, and screen measurement discards non-finite painted bounds so preview overflow always remains finite. This policy never rewrites imported skin source or changes `[data-core]` geometry or hit testing.
- Placements retain independent `textFitMode`, `textAlignment`, `textSizeOverride`, `minimumFontSize`, `textOffsetX`, and `textOffsetY`; null text size uses the skin's authored size, while the minimum is only the lower bound used by Shrink and Shrink and Stack. Button Text exposes horizontal `Use skin`, `Left`, `Center`, and `Right` alignment, direct pixel X/Y movement, and the placement cycle's logical-state dropdown for editing each state label. The renderer moves only the host-injected label node: static HTML labels use flow-preserving relative X/Y positioning, already-positioned HTML labels retain their authored positioning model and compose the host offset, and SVG label lines convert the requested screen-pixel vector through the live SVG matrix before applying host-owned positions. This stays valid even when an authored visual state changes the core between inline, block, flex, or grid layout, and regardless of whether `{{label}}` is directly in a face or nested in authored inline markup; it never rewrites skin source, authored transforms, `[data-core]` geometry, or hit testing. Every Button Text change is reflected immediately in its working preview. The single `Apply All` at the bottom of Button Text commits every pending Button Text edit across the editor: base labels or placement-cycle state labels plus each placement's fit, alignment, size, and X/Y position. It preserves state IDs, triggers, visuals, skin source, Button Size, and placement geometry. Static explanatory paragraphs are omitted; concise hover tooltips describe controls. The raw Base, Hover, Play, Pressed, Held, Release, Disabled, and Error code sections remain directly author-editable, including Hover. Skin paste and section edits stay in an isolated Skin Editor working copy until an explicit action. Recognized skin source applies through both native paste and the WebView textarea's normal input path, renders in an always-visible working preview, distributes into the canonical section editors, and clears the transient paste field; unparseable paste remains available for correction. The toolbar order is `Assign Skin`, `Assign Skin to Panel`, `Load skin`, `Save skin`, and `Save as new skin`. Load lists machine-local recent files first, saved library skins second, and `Browse...` last; every choice changes only the isolated working copy. Browse, first-time Save skin, and Save as new skin share `flowcellbackend/local/Button editor/Skins` as their native picker default. A successful load or save moves one deterministic `{ path, skinId }` association to the top of an eight-entry machine-local recent list without putting absolute paths in canonical Button state. Save skin overwrites its associated file, or opens the shared picker when no file is associated, then updates the same unassigned library skin. Save as new skin always opens the picker, writes canonical paste-ready `.flowcell-button-skin.txt` source, and creates an unassigned library entry whose name is exactly the chosen filename stem. Assign Skin writes only the focused placement's `skinOverrideId` and never changes `ButtonRecord.defaultSkinId`; an edited shared source, including the document-wide default skin, is forked first so other placements do not change. Assign Skin to Panel targets every Button on the focused placement's current surface, matching Assign Size to Panel across Main, Pop, Fan, and tool-set Pop occurrences. Skin/assignment saves are scoped canonical commits that retain unsaved arrangement geometry and activation cycles. Pasted recognized skin payloads use validated named-section semantics; there are no Apply Named Sections or Replace Entire Skin buttons. Before changing shared skin source, the Editor resolves inherited `defaultSkinId` use and keeps the safe default as a focused-placement override; a global or panel-wide assignment requires an explicit action and its wider blast radius is visible first.
- Visual overflow and active visual state are measured separately from the interactive core. Pop/Fan hover, press, hold, and play paint through the resting semantic frame's visible overflow without resizing or repositioning that frame, so transient skin motion cannot make the Button arrangement flicker or move. The authored skin and fixed native host bounds remain unchanged while DOM and native hit testing follow the live `[data-core]` rectangle outside an active press; after pointer-down, native input remains enabled through pointer-up even if transient motion moves the core.
- A mounted skin's shadow DOM is stable: it remounts only when the compiled skin identity (skin id + source fingerprint) changes. Rendered state-label and text-fit changes update the existing label node and rerun fitting in place, so cycling labels never replace `[data-core]` during input. Text offsets are reapplied across visual-transition frames so state-authored translation or SVG scale cannot stale their composed screen-pixel position. Parent re-renders, re-cloned documents, recreated callbacks, and placement resizes never rebuild the skin (a rebuild restarts every skin animation). Host pointer/keyboard listeners likewise stay attached across re-renders, and transparent Pop/Fan windows synthesize the `pointerleave` a cursor-ignoring window would otherwise never deliver.
- For an unchanged compiled skin identity, the skin renderer applies state attributes, cycle labels, placement hover brightness, and visual-measurement state as one latched presentation. A presentation with running finite CSS transitions or animations remains intact until that motion finishes, while later hover/press/hold/release/cycle requests collapse to the newest desired presentation. Raw pointer hover/press attributes, native `[data-core]` hit testing, and backend action dispatch remain immediate; infinite-only motion is nonblocking, and another activation does not restart or queue an active Play visual. A skin ID or source-fingerprint change resets the latch so new compiled source can mount. This host-owned behavior does not rewrite skin source, resize `[data-core]`, or change native coordinate mapping.
- Skin source, validation, compilation, and rendering live only under `FlowCellFrontend/src/button/skins/`; there is no separate skin registry.

Program And Bridge Runtime
--------------------------
- Startup preflight reads `Programs/*/flowcell.program.json` but validates immutable catalog/support directories, declared runner adapter files, mutable roots, and refreshed bindings only for programs already registered in `flowcellbackend/local/bindings.ini`; an available package alone has no runtime presence.
- The resident AutoHotkey backend launches the Windows Temp Shots overlay directly, then starts the installed package's sibling PowerShell saver asynchronously; cancelling one snip does not block the next launch.
- Each registered program selects its transport through `flowcell.program.json`; runner code may know that transport but never owns a pre-baked script or Button inventory.
- The Windows script runner keeps canonical ownership validation intact, then converts Rust's extended-length (`\\?\`) source spelling to the equivalent ordinary DOS/UNC path before launching child processes so Windows PowerShell 5.1 can resolve `$PSScriptRoot` and adjacent package files.
- Catalog execution targets are closed to a small product-neutral allowlist. Page services are declared separately as strict installed-page actions and become reachable only through the validated capability and active identity of an installed owner package.
- Generic installed-page services such as file/folder selection, palette sampling, declared field/package storage, owner state, and generated-Button installation are available only through a currently installed page's validated capability and active identity. Program actions are delegated to the registered runner/capability adapter; Core does not register product compatibility actions.
- Save Clipboard Text is a shareable, repeat-installable Windows single-script package: each Button accepts only clipboard text, writes a collision-safe timestamped UTF-8 file, keeps an independent destination in its owner-preserved `runtime/` state, and can reselect that folder while Shift is held (with a user-local fallback for standalone use).
- Codex Micro is a catalog-only set of closed Windows script packages. Its independently installable entries use the installed Codex desktop package's exact AppsFolder identity and coordinate-free UI Automation controls for verified task, dictation, navigation, stop, reasoning, and read-only status actions; dynamic numbered slots and unverified approval commands are documented but intentionally have no runnable entries.
- Blender installs require a top-level `run_flowcell_action(context=None, data=None)`. Deployment generates an owner-scoped bridge action from the installed Local source.
- Blender Rename Selected opens its multi-object prompt asynchronously through Windows PowerShell/WPF, then applies the confirmed names on Blender's timer; it does not depend on Blender's optional Tkinter runtime.
- Named Blender button events execute their declared bridge actions. A declared `pressDown` owns activation instead of also firing the normal release click; paired `pressDown`/`pressUp` events run in order and synthesize their declared hover session for keyboard use. Cycle Collection captures its private visibility baseline on hover, shows one object while held, restores object plus collection-layer visibility on release, and clears the private snapshot on leave without touching the manual baseline.
- The installed Blender Alignment Tool Set normalizes every child slot into an explicit axis/mode command. The active object remains the reference target, other selected objects move, and Origin slots use each moved object's origin as the source while still targeting the active object's bounds center.
- Blender actions that remove or replace Blender data capture response metadata before invalidating the corresponding RNA references; Split strips Blender's generated `.###` suffix and names results `<source> 1` through `<source> N`.
- Blender bridge/add-on deployment changes require reloading the FlowCell add-on or restarting Blender before runtime verification.
- Base Blender add-on repair preserves the installed owner-action registry and `ManagedActions` directory instead of replacing them with empty bundle templates. Blender owner install/sync reads UTF-8 source and registry files explicitly, passes each runtime wrapper its installed source-package root, and validates registration without executing program actions. Bulk recovery can register sources with `Install-BlenderFlowCellButtons.ps1 -SkipSync`, then normalize the completed registry once.
- Tool-set child payloads merge manifest defaults, child defaults, and live Button field/behavior values; child slots are validated against the active record. A child hotkey therefore carries the same current field state, state-only patches, file activation, payload template, and core action as activating that mounted child onscreen. On Run surfaces, children with `fieldPatch` or `toggleFields` automatically use the skin's authored pressed state when their declared values match the live fields, so fixed patches can form radio groups while a toggled choice that clears its peers can also return the group to no selection. A state-only `inlineEditField` child edits one hidden number/text value inside the real Button's injected label node, preserving its canonical placement, skin, `[data-core]`, movement, resizing, and authored animation; pointer-down anywhere on that core explicitly focuses the native popout before refocusing/selecting one stable editor node through pressed/release rerenders, and a separate `activationPatch` can reset values without affecting selected-state matching. Illustrator Ill Align uses independent X/Y three-state modes: neither (the default), Origin, or Surface. Selecting Surface or Origin releases its same-axis peer; clicking the active choice releases it back to neither. Min/Max consume that axis state, Center always aligns centers, and the neither state performs ordinary matching-edge alignment. Its command-file actions use the nonblocking persistent Illustrator bridge. Illustrator Rotate treats Art and Anchor as selectable pivot modes for subsequent Positive/Negative actions, accepts both current and legacy pivot payload names, and uses the nonblocking Illustrator process runner. Its original movable 30/45/90 instant-angle Buttons remain separate actions that force Transform and preserve their established Illustrator direction. A tenth movable, skin-authored inline value Button sits alongside them: Transform resets it to 90 and Distribute resets it to 3, while either mode accepts a directly typed replacement.
- The Illustrator Layers Builder panel remains 19 independent single-script owners. Its versioned catalog contributions update installed owners in place without changing IDs or converting the panel to a tool set. Eight actions are document-global and need no Layer Tree highlight: Make Layers, Sort, B Lock, B Vis, Set Lock, Set Vis, Empty Sublayers, and Empty Trash. The other eleven validate exactly one active generic `illustrator.layer-tree` owner and resolve its strict saved keys directly to Layer references, avoiding synthetic artwork selection and its hidden/locked-state corruption. Snapshot alone may use a nonempty native Illustrator selection when the validated owner state has no highlighted rows; the other ten targeted actions fail closed. Sort protects and orders all five system roots, New Sub targets an exact highlighted parent and reaches its naming prompt without invalidation racing away that saved target, Delete Sublayer protects system roots and Archive/Trash contents, and Empty Trash confirms destructive clearing. New Sub alone declares completion-wait execution: its bridge work runs off the Tauri main thread, and the standard program-data invalidation is emitted only after its naming prompt closes and Illustrator has created the layer. The separate ordinary Layer Tree page names new children before creation and lets a row be dragged onto another layer (for example Live) to move it inside through the declared `move` capability. The Illustrator capability adapter normalizes ordinary and Windows extended-length (`\\?\`) paths before enforcing the Button-owned Local Scripts boundary.
- The registered Illustrator runner starts its persistent package-owned bridge in the background and sends both ordinary Button/tool-set actions and request/response page capabilities directly over its named pipe, avoiding per-click AutoHotkey COM setup and per-request PowerShell startup. Its versioned `v2` pipe and response protocol prevent an older detached bridge from being accepted after an update. The PID file is diagnostic only: pipe responses and the named process mutex determine live ownership, so a stale but live PID cannot suppress startup. FlowCell starts the bridge without launching Illustrator, then a native background watcher prewarms the cached COM proxy as soon as an Illustrator window exists and repeats that prewarm whenever either the Illustrator PID or verified pipe-owner PID changes. Warm state follows the live bridge PID returned by the pipe, so a stale file cannot trigger continuous prewarming. Pipe-busy errors are distinguished from a missing bridge, and the process mutex plus pipe-ownership check makes duplicate bridge launches exit without overwriting ownership state or spinning. A Button that races the one-time background prewarm waits for it rather than failing busy; otherwise ordinary actions receive a nonblocking acceptance response, while capabilities wait on the serialized bridge so post-action refreshes observe completed Illustrator state. The bridge validates its cached COM proxy before use and, when an action reports the specific stale-server `0x800706BA` disconnect, discards that proxy, reacquires the current Illustrator application, and retries once. Ordinary Illustrator script errors are not automatically replayed.
- Program-owned capability adapters and runtime registrations exist only while an exact active installed owner declares them; owner deletion removes those artifacts through the standard source transaction instead of leaving a Core fallback.

Managed Windows And Layouts
---------------------------
- `FlowCellFrontend/src/button/windows/`, `FlowCellFrontend/src/button/animations/`, `FlowCellFrontend/src/lib/windowContext.ts`, `FlowCellFrontend/src/lib/layoutSnapshots.ts`, and `FlowCellFrontend/src/AppBase.tsx` own Button editor, popout, fan, and transient activation-presenter window creation/routing/restore.
- Illustrator-scoped popouts temporarily detach their native owner while Windows taskbar previews are active, retain the real Illustrator owner through that preview, and restore it afterward so activating another program immediately returns the popout behind Illustrator.
- Program-scoped Pop, Fan, and installed-page windows use one native placement state machine. An explicitly opened Pop/Fan receives a post-show normal-band reveal tied to the opening FlowCell window and then to the revealed window itself. Only an exact manifest `processNames` match for the actual foreground process may select `TOPMOST`; transparent Pop/Fan windows otherwise remain in the normal band with geometry-selective input even when the owning program is closed or inactive, preventing visible controls from passing clicks to unrelated windows underneath. Opaque installed pages retain normal input and may continue in the normal band when focused. Installed pages use standard native chrome for dragging, minimizing, and closing. Taskbar previews still suppress input and demote every scoped window behind the real foreground HWND (or to the bottom as a fail-safe), while Illustrator's exact foreground match retains its owner-bound topmost behavior. Scoped-window IPC commands that share the native placement worker's apply lock execute off the main thread, preventing WebView focus callbacks from deadlocking against worker-dispatched Tauri window access.
- Layout restore and collapse/expand use saved physical-pixel managed-window bounds and canonical Button surface identities, preserving mixed-DPI size and owner anchors. Restore resolves its target program and panel before exposing either selection, then performs a request-scoped source refresh; whichever matching refresh wins also consumes the target-scoped saved Button selection, including an explicitly empty selection, instead of relying on unchanged React dependencies to reload cleared Buttons.
- Pop and Fan setups save a `surface`, `hitbox`, or `visual` window-fit mode. Their non-resizable transparent Tauri host is a large fixed canvas covering the active monitor work area (and any semantic frame outside it), starts cursor-ignored, and becomes cursor-active whenever the pointer is over a Button host, tool field, or Pop resize handle; after a Button receives pointer-down, the host stays cursor-active through pointer-up even if an authored animation moves the live core away. Owning-program state controls native topmost promotion, not whether a visible control can be clicked. Transparent gaps still pass clicks to the application underneath, and taskbar-preview suppression still disables the host. Hitbox/visual fits, hover/press/hold/play overflow, Fan expansion, and tool-set collapse/expansion move and resize only an absolutely positioned semantic content frame inside that canvas, preserving one invariant physical surface origin instead of repeatedly moving the HWND. The canvas grows or rehomes only when content would escape it, including monitor-edge drag/resize and mixed-DPI transitions. An unsized Pop starts at one design pixel per WebView CSS pixel; restored physical bounds use the destination WebView's effective pixel ratio, and scaled skin measurement retains skin-root and animated shadow/outline scale while normalizing ancestor content scale into design units. Hold Space and drag any visible Button to move the semantic frame; an expanded tool set stays expanded throughout that drag and persists the expanded placement, while Pop corner handles preserve aspect and the opposite corner. On release, real physical-pixel Pop/Fan bounds and semantic layout snapshots persist, while transient active envelopes and the large native canvas bounds never do.
- One shared native input worker samples cursor and modifier state and emits only changed snapshots; each Pop/Fan reacts to those changes plus local geometry/DOM invalidation instead of polling native input every frame. Scope and input listeners subscribe before querying their initial state, retry transient setup/read failures, and fail closed to cursor-ignored; the serialized native cursor-style controller also retries a failed `setIgnoreCursorEvents` call and converges to the newest requested state. Newly created transparent windows initialize cursor-ignore fail-closed, while reopening an existing window leaves its live hitbox controller in sole ownership of that flag; Pop/Fan hitboxes start only after final canvas placement completes. Physical semantic bounds and cursor snapshots are mapped through the WebView's effective pixel ratio (including WebView zoom, with native DPI as fallback), so fixed-canvas placement and synthetic hover stay aligned. The window rejects pointers outside its semantic frame before consulting cached interactive membership, but reads exact viewport rectangles live after position-only frame movement, and it bypasses the render barrier for unchanged envelopes. Active visual overflow is measured only while the authored subtree has running motion plus final settle frames, so finite hover/play transitions stop consuming animation-frame work without changing skin source or hitbox ownership.
- Layout snapshots are strict version 8 `FlowCellWindowLayout` documents and accept only Button editor, popout, and fan windows.
- The transient activation setup/runtime presenters are intentionally outside global layout snapshots: they exist only while configuring or playing, and the last physical bounds persist with the canonical Button assignment.
- The frameless Buttons Editor window renders its own title bar (all load/error/ready states): drag the bar to move, double-click it to maximize/restore, with minimize, maximize/restore, and close controls. Close routes through the window's close-requested handler so unsaved placement, skin, and animation drafts follow the normal cancellation path. Layout capture/restore and ordinary reopen reject Windows' `-32000` minimized sentinel bounds, discard stale registered snapshots, and recover the Editor at its default placement.
- Other FlowCell utility windows remain managed Tauri windows but do not own a separate Button implementation.
- `FlowCellFrontend/src-tauri/capabilities/default.json` must list every managed or transient window label and every window/webview command the frontend calls, including the managed Add Program and Add Panel setup windows, the activation presenter, both background-color grants for transparent windows, and the force-destroy grant used only after Editor cleanup; a missing grant surfaces as a runtime "not allowed" ACL error, and changes to it require a Tauri rebuild.

Validation
----------
- Frontend/Tauri changes: run the relevant frontend build; use `flowcellbackend/helpers/Start-FlowCellFrontend.ps1` with `-ForceRestart` when the running frontend must refresh.
- Rust changes: run `cargo check` plus focused tests.
- AutoHotkey changes: validate with AutoHotkey v2 and restart the hidden backend.
- PowerShell changes: parse-check touched scripts and run the narrow behavior test when practical.
- Blender source/bridge changes: compile-check Python where applicable and verify after add-on reload or Blender restart.
- Documentation-only changes: validate headings, links/paths, and stale-term removal; no application build is required.
- Portable program ZIPs contain only Git-tracked package files, require a tracked program manifest, and reject manifest-declared mutable folders, reparse points, containment escapes, and unsafe archive members; the Core ZIP contains no `Programs/` payload.
