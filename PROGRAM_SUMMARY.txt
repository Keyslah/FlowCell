FlowCell Program Summary
Last updated: 2026-07-01

Purpose
-------
FlowCell is the desktop frontend, command host, program folders, local runtime state, and Blender bridge workflow.

Current frontend state
----------------------
- Dynamic Organization has a role-based backend and frontend resolver. Setup Organization opens the managed `organization-setup` Tauri/React window by intercepting the panel script filename in main-panel activation, the shared panel-script runner, and the backend response path, while the full PowerShell setup UI remains a standalone fallback. The left sidebar is two separated panels side by side: a Root folder panel (root rail + the root folder tree + Delete folder / Undo) and a Load profile panel (load profile rail + the loaded profile's tree + its own Delete folder / Undo). Only one folder is selected at a time across both trees — selecting a folder in one tree clears the selection in the other, so a single "active folder" drives the editor. Delete folder sends the selected folder to the Recycle Bin (the on-disk project folder, or a folder in the saved profile skeleton; for an unsaved scratch profile tree it just drops the folder from the in-memory list), and Undo reverses the last folder add/delete (restoring deleted folders from the Recycle Bin best-effort). The root rail's Apply profile button builds the loaded profile's structure into the selected folder — the root (also writes the profile) or any subfolder (folders only). Clicking a folder in either tree shows that folder's assigned roles/folders on the right (the editor card follows the active selection, so you can view and edit a profile folder's assignments too). The Load profile rail's Copy root to profile button mirrors the current root folder's folder structure into the profile section as an unsaved scratch tree you can view/edit before saving it as a named profile; the disk-writing project-only actions (Delete folder under the project tree and Apply profile) stay scoped to the project tree, while Add Folder targets whichever tree's folder is active. The footer has Apply to tree (write the profile to the root folder), Apply to profile (save the current setup into the loaded profile, to build it up incrementally), and Apply & rescan. Roles are assigned from a Role dropdown and list as compact rows (Name | file types | Edit / Unassign / Delete) showing every assigned file type; folders added to the selected folder appear in the same list (tagged "Folder"). Program folders (those carrying file types) are grouped under their build root `01 src` — where the apply step actually creates them (e.g. `01 src/Illustrator`) — so they show when `01 src` is selected rather than under the root folder, even if the saved rule stores a bare name; plain folders and folders with an explicit parent keep their literal parent. Add Role opens a popup with a Role name / File types row, grouped file-type picker buttons (Images, 3D Files, Illustrator, Blender, Fusion 360, GCode/CNC, Reference/Documents), an Add File Types action, and Save File Group which stores reusable custom groups in browser localStorage. Add Folder (next to Add Role) opens a popup that adds any folder name to the active folder in either tree (file types optional): Add folder creates it immediately and rescans so it shows in the tree; Add when files match makes a conditional rule created on apply. Where "Add folder" materializes depends on the active tree — a project folder creates it on disk under the root folder, a loaded saved profile folder creates it in that profile's on-disk skeleton (so it sticks), and an unsaved "copy root to profile" scratch folder adds it to the in-memory tree (kept on Save Profile). Because the profile section is the source of truth for a loaded/scratch profile's folders, Save Profile / Apply to profile re-save that tree (not the project tree) so folders added there are never wiped. The popup also lists saved profiles — clicking one builds that profile's structure into the selected folder. Folders with file types show a substructure preview in their assigned-list row (01 live / 02 snapshots / 03 archive / 04 trash) so you can see what will be built. A direct File Types input assigns types straight to the selected folder. The footer Apply to tree button writes the profile to the current root folder. The Don't Remove Files control is rendered natively in the React setup page and saves selected protected folders into the profile, so picking a new root folder no longer relies on runtime DOM patching. The preset `unknown` role must be assigned to a scanned folder before saving (shown as a bottom warning, not a popup); unmatched loose files fall back to `unknown`, while files matching multiple roles open a scoped file/run/project choice prompt.
- The per-project profile is a single visible file `<root>/organize-folder.profile.json` (legacy `.flowcell/organization-profile.json` is still read as a fallback and migrates on the next save); both the Rust commands and `Dynamic-OrganizationCore.ps1` use it. It is written as UTF-8 without a BOM, and the Rust reader strips a leading BOM so PowerShell-written profiles still parse. Save Profile stores a named, reusable copy in two places: a clean empty folder skeleton (folder structure only) under `FlowCell/local/Folder Trees/<name>/` and the profile data under `FlowCell/local/Folder Tree Profiles/<name>.json`. Load profile loads a saved profile's rules into the editor without changing the project root; Apply profile to root builds that profile's folder structure, writes the profile there, and applies conditional program-folder routing without deleting or overwriting files. Make button generates the apply-profile script (`Programs/Windows/Windows Git Scripts/Files/apply_profile_<slug>.ps1`, backed by `Programs/Windows/SupportScripts/Apply-OrganizationProfileCore.ps1`) and drops it straight into the Windows `Files` panel as `<ProfileName>.ps1`, so a panel button named after the profile appears (reselect the Files panel to refresh); clicking it applies the profile to a clipboard folder path. The name `setup_organization` is reserved for the launcher button.
- The starter profile assigns nothing to any folder. It has the required `project_root` and `unknown` presets plus three default roles available in the Role dropdown — Images, SVG, 3D (each with its file types, unassigned) — and no program folders. The four program defaults (Illustrator .ai/.ait, Photoshop .psd/.psb, Blender .blend/.blend1, Fusion 360 .f3d/.f3z) are only quick-fill presets in the Add Folder popup and are never auto-added. Added folders persist as `programFolders` entries. Applying a named profile (`Apply-OrganizationProfileCore.ps1`) places each program under `01 src` beside `00 assets`, names it `NN <Program>` (reusing an existing unnumbered match), and always adds `01 live`, `02 snapshots`, `03 archive`, `04 trash`. Only working files inside `01 src` plus loose files dropped at the project root (which get filed into `01 src`) are eligible to be routed — every `01 src` sibling (`02 builds`, `03 releases`, the big top-level `04 archive`, etc.) is left untouched, and any program's own `02 snapshots`/`03 archive`/`04 trash` (with or without a number prefix) is skipped so already-filed, archived, or trashed files are never pulled back into `01 live`/`02 snapshots`. Within a program, files are grouped by extension then by family name (`Get-DuplicateInfo` strips trailing copy/version/final markers): the newest member of a versioned family goes to `01 live` and older members go to `02 snapshots` as `<base> (Snn)`; everything else goes straight to `01 live`. Moves are verified and non-destructive (conflicts recorded, never overwritten).
- The main-page Add Program flow accepts either a pasted EXE path or the folder containing the EXE; leaving the paste prompt blank opens a folder picker. The desktop host resolves the primary executable, including preferring `blender.exe` over Blender launcher/helper executables, before registering and bootstrapping the program.
- The main FlowCell window (frameless, `decorations: false`) supports hold-Space-and-drag to move it, the same convention used by the toolbox/popout windows: holding Space sets a grab cursor, and dragging while held calls `startDragging()` on the current window. The handler lives directly on `MainPage`'s root `<main>` element (`onPointerDownCapture`), so it does not interfere with normal button clicks when Space is not held.
- Windows program panel scripts run without first activating `explorer.exe`: the backend treats Windows/explorer/DOpus-backed generic programs as `windows_generic`, so scripts such as monitor toggles can run without pulling a File Explorer window back to the foreground.
- The default Ctrl+Shift+F2 "single-monitor" shortcut (auto-bound to `Programs/Windows/Panels/Utility/Toggle Monitors.vbs`) is now persisted to `FlowCell/local/bindings.ini` the first time `FlowCellBackend.ahk`'s `EnsureDefaultSingleMonitorBinding` restores it, instead of staying in-memory only — previously the Binds UI (which reads `bindings.ini` directly) always showed it as unbound even though the hotkey worked. `ShortcutManager.SaveToDisk()` also now re-normalizes the file to UTF-8 after writing (AHK's `IniWrite` recreates files as UTF-16, which the Rust `read_bindings_file_state` strict-UTF-8 reader cannot parse at all). The frontend's own fallback default-binding resolver (`resolve_single_monitor_binding` in `main.rs`) was pointed at a stale, nonexistent `Programs/Windows/toggle_monitors.ps1` path from an older version of this feature; it now points at the same `Toggle Monitors.vbs` the AHK side uses. Separately, an unrelated legacy "Dummy Monitor Toggle" feature (the predecessor to Toggle Monitors) left orphaned backup files in `Windows Local Scripts`/`ScriptDump`, an orphaned `__pycache__` entry, and a dead Windows Startup shortcut pointing into an unrelated `computerideas` repo; all were removed (Recycle Bin), along with stale `%LOCALAPPDATA%\ToggleMonitors\` snapshot/profile leftovers from that era.
- Windows PowerShell launches are hidden across the shared runners: the AutoHotkey command backend always runs `.ps1` panel scripts with `-WindowStyle Hidden` plus AutoHotkey's hidden launch flag, the Tauri PowerShell output helper uses `CREATE_NO_WINDOW`, the FlowCell VBS frontend/backend launchers pass hidden PowerShell startup flags, and STA self-relaunching Utility scripts use `ProcessStartInfo.CreateNoWindow` so no blue PowerShell console should flash during panel-script actions.
- The Windows Utility panel includes `Temp_Shots.vbs` as the visible Temp Shots button (`Programs/Windows/Windows Git Scripts/Utility/Temp_Shots.vbs`, mirrored into `Programs/Windows/Panels/Utility/` and `Programs/Windows/Windows Local Scripts/`) so FlowCell launches it through `wscript.exe` without a console and without a space-bearing script path. The launcher starts `Temp Shots.ps1` hidden and returns immediately for normal captures so shortcut bindings are not blocked while Windows screen snip is open; validation mode still waits for an exit code. After a Temp Shots folder has been selected, the hotkey path opens Windows screen snip directly from the resident AutoHotkey backend, then starts the hidden PowerShell saver in clipboard-wait mode so PowerShell startup no longer delays the snip overlay. The PowerShell implementation clears older Temp Shots runner processes before waiting, prompts once for a screenshot destination folder, stores that choice under `FlowCell/local/windows/temp-shots/temp-shots.config.json` plus a no-BOM `temp-shots.folder.txt` fast-path cache, then saves each captured clipboard image as a timestamped PNG and writes the result to `FlowCell/local/logs/last_action_status.txt`. FlowCell reads `FlowCell/local/bindings.ini` with a BOM-tolerant parser before shortcut registration so BOM-prefixed binding files still load saved hotkeys.
- The Blender Theme toolbox stages theme buckets from an image, absorbed Blender theme values, dark/light presets, per-bucket swatches/eyedroppers, hex fields, and per-bucket apply buttons. The top theme `Browse` now samples the chosen image, copies that same path into the Place Picture field, and immediately runs Place Picture in Blender; the bottom Place Picture row remains separate and still has its own `Place Picture`, picture path input, `Browse`, `Startup`, and `Clear` controls that do not change theme buckets. The `Startup` button saves the current Place Picture image to the global startup state file (`flowcell_theme_startup_state_v1.json` in Blender's CONFIG dir); on each Blender launch `flowcell_actions.py` re-registers the `load_post` restore handler and polls, calling `read_place_picture_runtime_state` then `restore_project_startup_state` on the `flowcell_custom_theme` action, whose `_restore_project_startup_state` reapplies the saved picture. Two bugs kept this from working: (1) a misplaced grid-clamp loop had been pasted into `_ensure_project_theme_restore_handler_registered_from_action` (referencing `place_picture_state`/`state`, out of scope there), so every save raised a swallowed `NameError` before the handler could register — that loop was moved into the state-normalization function (where those names exist and it also clamps `grid_distance_m`/`grid_far_spacing_m`); and (2) the theme script had **forked across its copies** — the generated runtime/installed copy had been hand-edited to add the restore subsystem (violating the "never edit ManagedActions as source" rule) while the `Blender Git Scripts/toolset/theme.py` source lagged behind and never gained it, so the copy Blender actually ran depended on which stale generation was installed. All four copies were reconciled to one canonical version (source `Blender Git Scripts/toolset/theme.py` == `ManagedActions/flowcell_custom_theme.py` runtime == `Blender Local Scripts/theme.py` backup == the installed `scripts/addons` copy, byte-identical): the complete restore subsystem + project/global startup-state model is kept, the dead `_remember_theme_bucket_state`/global-only-state helpers were dropped, and the `# FLOWCELL_CHILD` header keeps the current Save Buckets/Load Buckets labels. Going forward only `Blender Git Scripts` is edited and re-deployed via Add Script (which copies the source verbatim into `ManagedActions`); after any of these changes Blender must reload the FlowCell add-on / restart for startup restore to take effect. The single bucket Apply buttons route through the Blender theme action's `apply_theme_bucket` handler in the source/local/live theme scripts so individual buckets can apply without falling back to the full theme apply. The old visible Grid button and near/distance/far grid spacing fields are no longer shown, while the Blender bridge still accepts the stored grid payload values internally for compatibility. The custom-action sync restores configured bundled Blender actions from the repo registry before regenerating the live registry, so the `flowcell_custom_theme` button is restored from its source-backed runtime entry without relying on the old `custom_hdri_world_tools` alias. Place Picture overlay drawing is generation-gated, and Clear invalidates active/stale generations so the background, fake grid, and fake gizmos stop drawing after cleanup. The theme status message is a short-lived toast that clears itself after a few seconds, and the native theme toolbox window auto-fits to the measured visible toolbox content on open so the transparent area below the controls does not block desktop clicks. Save Buckets opens a single native save dialog (pre-filled with a default theme file name) instead of also showing a separate name prompt. Refill re-rolls role colors by sampling only from the stable sampled palette and no longer folds the current role colors back into that palette, so repeated refills stay varied instead of drifting toward grey. While a native color/eyedropper picker is open the theme window stays fully suspended from the scoped-topmost worker so the eyedropper works over any monitor (including Blender's) without the taskbar/topmost flicker. The capture-phase shell pointer handler no longer re-registers scoped topmost on the click that opens a color picker (that registration used to race and beat the picker's suspend), the window-focus handler no longer re-registers while a picker is open, and scoped topmost resumes only when the picker actually closes (color input blur, Escape, or a click back inside the window). The scoped-topmost worker is now idempotent: it only re-issues the native always-on-top/SetWindowPos calls when the resolved state changes (target gains/loses foreground, cursor crosses the taskbar, or owner change) instead of every ~180 ms poll, which stops the continuous z-order churn that flickered the taskbar while Blender was foreground.
- Blender Add Script treats `Programs/Blender/Blender Git Scripts` as the source library and `ManagedActions` as generated installed runtime output. Add Script accepts ANY Blender source that exposes `run_flowcell_action(context=None, data=None)` — a single script, a toolset, or a thin wrapper whose `run_flowcell_action` calls `bridge.execute_bridge_operator(...)` — and installs, deletes, and re-adds them all through the same path, so every button (including the formerly "built-in" ones like snapshot/sort/back/trash) is a first-class Add Script citizen. The old `FLOWCELL_BUILTIN_ONLY` marker, the bridge-wrapper rejection, and the installer's built-in action/description maps were removed; bridge wrappers work because the referenced operator lives in the installed add-on (`flowcell_bridge.execute_bridge_operator`). Add Script records `pythonPath` as the runtime copy and `sourcePythonPath` as the real selected source, preserves `FLOWCELL_KIND`/`FLOWCELL_CHILD` metadata, and the bridge prefers registered scripts before built-in compatibility fallbacks. The bundled Blender config/registry is pruned to the active source-backed custom actions; old `custom_*`, stale `_2`/`_3`/`_4`, util alias, panel-copy, and bridge-only ManagedActions variants are removed instead of kept as hidden runtime source. Alignment Tools and Flatten/Revolve are self-contained in `Blender Git Scripts/toolset/` and mirrored into checked-in runtime copies. Deleting Blender buttons calls `delete_blender_action(action_id)`, removing config entries, registry entries, unreferenced generated ManagedActions files, and stale same-family variants before verifying no dangling config or registry references remain. Blender may need an add-on reload/restart after Add Script, delete, registry, bridge, or ManagedActions changes. (2026-06-30 the installed add-on's `ManagedActions` had drifted to 86 `.py` files from repeated Add Script runs; it was pruned back to the 24 registry/button-backed actions — old `custom_*` engines like `custom_hdri_world_tools.py`, now-built-in action copies such as `snapshot`/`sort`/`back`/`trash` and their `_2`.. dupes, and `util_boolsafe_*` variants were recycled — and the repo deploy copy lost 6 stale `_N` dupes, matching the pruning policy above.)
- The Blender Files panel Save STL, Cura, Orca, and generic Slicer buttons export selected mesh objects to the active project's organization-profile destination for `.stl` files: the matching program folder's `01 live` folder when `.stl` is assigned to one program folder, the matching/remembered role folder otherwise, or `01 src/00 assets/03 3d` when no profile route exists. The exported path returned by Blender is the exact file path passed to FlowCell's slicer launcher.
- The Blender Files panel Cura and Orca buttons export selected mesh objects to STL, then FlowCell uses a confirmed slicer executable path. On first use, or when the saved path no longer exists, FlowCell prompts to confirm the auto-detected slicer EXE or choose a different EXE; confirmed paths are saved separately in `FlowCell/local/cura_launcher.json` and `FlowCell/local/orca_launcher.json` for later launches. If Blender is not running, FlowCell stops before the slicer prompt and tells the user to open Blender first.
- A generic Slicer button (`Programs/Blender/Blender Git Scripts/Files/slicer.py`) exports selected meshes to STL and asks FlowCell to launch a user-chosen slicer EXE. FlowCell treats its `slicer_id: "slicer"` response as a generic launcher instead of coercing it to Cura or Orca; it accepts any chosen `.exe` and passes exported model files through the same launcher command path as the Cura/Orca buttons. FlowCell hands the exported STL paths to the slicer by launching the chosen slicer EXE with those paths as arguments and lets the slicer's own single-instance setting decide where they land — its running window when single-instance is enabled, otherwise a new window — so the model always loads. FlowCell does NOT force a `--single-instance` flag: when the user's slicer has that option turned off (e.g. OrcaSlicer's default `single_instance: false`), forcing it makes the launch try to hand off to a window that is not listening, so the files are silently dropped and nothing loads. FlowCell also no longer posts a cross-process Windows file-drop/`WM_DROPFILES` message, which silently failed — the drop handle is only valid inside FlowCell's own process, so the slicer never received the files even though the post reported success. This does not change the Blender-owned button window's scoped topmost behavior. Each slicer button instance owns its own executable assignment, keyed by program/panel/file in browser localStorage (`flowcell.slicer.buttonAssignments.v2`, so stale v1 assignments no longer suppress first-use prompts). The first click on a button with no assignment opens a native slicer chooser with spaced one-click buttons labeled only by slicer name for the script-detected slicer, recent slicers, and detected installed slicers from standard install roots plus Windows installed-app metadata, plus a `Browse...` button for any other `.exe`; chooser choices filter out helper executables and collapse each known slicer family to its latest discovered version, including stale recents left by older builds. Full paths are only tooltips. It then uses the native text dialog to name the button and saves that button's assignment. Later clicks launch directly; if a saved assignment is malformed or points to a missing slicer EXE, FlowCell clears that button assignment and prompts again. Regular panel buttons, panel fan popouts, and grouped script popouts all run through the same slicer assignment path and surface returned script status messages such as unsaved-blend blockers or launch cancellation. On the main page a successful script status (e.g. "Sent 1 model file to Slicer.") shows as a small green toast that fades out on its own after a couple of seconds (`.main-page__script-status`), separate from the red dismissable error box (`.main-page__script-error`) which is still used for actual failures; the fan and grouped-script popouts still show the dismissable box. Recent slicers (`flowcell.slicer.recentExecutables.v1`, max 8) are convenience choices only and are never auto-assigned, so multiple slicer buttons can point to different slicers. Deleting a slicer button through FlowCell clears that button's assignment. Assignment/recents/detected-installed-slicer handling lives in `FlowCellFrontend/src/lib/slicerLauncherAssignments.ts`, `FlowCellFrontend/src/lib/tauri.ts`, and `FlowCellFrontend/src-tauri/src/main.rs`; the existing Orca/Cura buttons still use their saved launcher paths.
- The legacy Organize Folder run (`Organize-FolderCore.ps1`) no longer writes `organize-folder.log.txt`; its full record (file moves, structure renames, recycled directories, duplicates, snapshots, conflicts, unresolved items, plus rollback data) is written to `organize-folder.undo.json`.
- Normal repository startup runs `FlowCell\helpers\Start-FlowCellPreflight.ps1` before reusing, building, or starting the frontend. Missing or failed preflight stops both normal and portable startup, core registration failures propagate instead of opening FlowCell with a broken program rail, and successful runs write a completion marker to `FlowCell\local\logs\startup-preflight.log`. Startup preflight repairs `FlowCell\local\bindings.ini` registrations for existing built-in program folders (Illustrator, Windows, Blender, and Photoshop), so a missing or damaged registry is repopulated from the folders on disk instead of coming back as Windows-only.
- `FlowCell\helpers\Start-FlowCellFrontend.ps1` decides whether to rebuild the Tauri frontend on launch by comparing the current source against two freshness files in `FlowCellFrontend\src-tauri\target\release` (`.flowcell_frontend_source_commit` = `git rev-parse HEAD`, `.flowcell_frontend_source_stamp` = a hash of source file sizes/mtimes); it writes those stamps only after its own `npm run tauri build`. A manual `npm run tauri build` therefore leaves the stamps stale and the next launch rebuilds again, so run `FlowCell\helpers\Update-FrontendBuildStamp.ps1` after a manual build to refresh the stamps (best-effort; on drift the only cost is one extra startup rebuild) so the next launch starts the existing binary without rebuilding. Reusing an already-running frontend now requires a visible real main Tauri window titled `FlowCell`; if the process is alive but only exposes internal windows such as the tiny Tao event target or tooltip handles, the launcher treats it as stale, stops it, and starts a fresh frontend instead of reporting a fake focus success.
- Layers Builder is a separate Illustrator layer/object manager that becomes the primary highlight-driven layer panel, leaving the original `Layers` panel fully intact as a fallback. It has three parts. (1) A warm-bridge JSX action `ill-layers` (`Programs/Illustrator/Illustrator Git Scripts/LayersBuilder/layers.jsx`) scans and mutates the document's layer/sublayer tree (scope: layers + sublayers only, no pageItems) and returns the fresh tree as JSON; layers are addressed by a dot-path "key" of layer indices (e.g. `0.2.1`) recomputed each scan. Supported ops: scan, create (top or sublayer), rename, delete (with `force` to temporarily unlock/unhide), duplicate, setlock, setvis, move. (2) The `Build Layers` window (`pages/build-layers/BuildLayersWindowPage.tsx`, window kind `build-layers`, opened via `openBuildLayersWindow`) is a frameless FlowCell window (decorations off — no native titlebar/min/max/close): hold Space and drag anywhere to move it, with edge/corner resize handles (`startResizeDragging`), like the toolbox windows. Its label `flowcell-build-layers` is listed in `FlowCellFrontend/src-tauri/capabilities/default.json` `windows` — required, or every `core:window:*` API (drag/resize/setSize) is silently denied for the window. Resizing uniformly scales the whole UI: the content is laid out at a canonical 360px width and a `transform: scale(windowWidth/360)` surface fills the window (the toolset surface-scale pattern). Each row has an Illustrator-style "target" circle on the far right; clicking it runs the `ill-layers` `select` op, which selects all artwork on that layer/sublayer in Illustrator (temporarily unlocking/unhiding) and makes it the active layer. Its content is chrome-light: just a toolbar (+ Layer, + Sublayer, Rename, Refresh, Duplicate, Delete, Force Delete) and the live tree (no title header, no bottom info bar; errors show as a thin red line only on failure). Click a row to select it as a FlowCell target, Ctrl/Cmd-click to toggle, Shift-click to select a contiguous range; selection is FlowCell-owned and independent of Illustrator's native panel, and locked/hidden rows are selectable. Each row has per-row lock/visibility toggles. The row whose key equals Illustrator's `doc.activeLayer` (returned by the scan as `active`) is shown bold — that is a fresh read of Illustrator's active layer on each scan, not a live subscription. Delete/Force Delete remove the highlighted layers directly by key (work on empty/locked/hidden layers). The tree scrollbar is visually hidden (`scrollbar-width:none` / `::-webkit-scrollbar{width:0}`) while still scrolling. The tree auto-refreshes after every FlowCell-initiated op, plus the manual Refresh button. It also re-scans when an Illustrator Layers / Layers Builder panel button runs: `runPanelScript` emits `flowcell:illustrator-layers-changed` (exported as `ILLUSTRATOR_LAYERS_CHANGED_EVENT`) and the window listens and re-scans twice (~350ms and ~1100ms, since the panel `.jsx` runs asynchronously in Illustrator after the click is accepted) — so e.g. clicking the `delete sublayer` panel button updates the window without a manual Refresh. Highlighted keys are persisted to `FlowCell/local/illustrator-layers-highlight.json` (and an OS-temp mirror) via the `set_illustrator_layers_highlight` Tauri command. The tree read/mutate path is the async `run_illustrator_layers_action` command (Tauri `async` + `spawn_blocking` so the possibly-multi-second cold-start PowerShell call never freezes the WebView), which invokes `Invoke-IllustratorFlowCellAction.ps1 -ActionId ill-layers -Wait` via `powershell -EncodedCommand` (base64 UTF-16LE — the only reliable way to pass the args JSON with embedded quotes through powershell.exe) and returns the bridge response JSON. The shared bridge client (`Invoke-IllustratorFlowCellAction.ps1`) sets pipe Read/Write timeouts best-effort because .NET Framework PipeStream does not support them (assigning them previously threw and broke every bridge call). (3) The `Layers Builder` panel (`Panels/Layers Builder/`, generated from the original `Layers` panel by `Programs/Illustrator/SupportScripts/New-IllustratorLayersBuilderPanel.ps1`) contains a self-contained `.jsx` copy of every original Layers button plus a `Build Layers.jsx` launcher (intercepted by `runPanelScript` to open the window). Most artwork-driven buttons get a selection prelude; structure-driven buttons listed in the generator's `$directBodies` map (currently `delete sublayer`) instead get a self-contained body that deletes/edits the highlighted layers directly by key (so they work on empty/locked/hidden layers, which the selection-driven originals cannot). Illustrator panels only run `.jsx`/`.js` and execute them inside Illustrator, so each generated button is a `.jsx`: the artwork prelude reads FlowCell's highlight set from the OS temp folder (`Folder.temp/flowcell-illustrator-layers-highlight.json`, written there as a mirror by `set_illustrator_layers_highlight`), resolves the highlighted layers to their real pageItems (temporarily unlocking/unhiding the layers and their ancestors), selects them, then the unchanged original Layers script body runs, and a `finally` block restores layer lock/visibility — so e.g. Snapshot works on highlighted locked/hidden layers. Re-run the generator after adding buttons to the original Layers panel to keep the two in sync. The tree action is registered in `Programs/Illustrator/illustrator-actions.json` (`ill-layers`).
- Window Grid is an overlay that lists every open FlowCell window as a card grid grouped by Program -> Panel. A launcher button `window_grid.ps1` lives in the Windows Files panel (`Programs/Windows/Windows Git Scripts/Files/` + `Panels/Files/`); `runPanelScript` intercepts it by name (`isWindowGridLauncher`, matching base name `window grid`/`windows grid`/`window-grid`/`all windows` with `_`/`-`/space treated alike) and calls `openWindowGridWindow` instead of running the script — so the trigger button can be placed in any panel. The window (`pages/window-grid/WindowGridWindowPage.tsx`, kind `window-grid`, label `flowcell-window-grid` registered in `capabilities/default.json`, created with `skipTaskbar: true` so it never adds a taskbar entry) is frameless with Space-drag + resize handles. It enumerates `WebviewWindow.getAll()`, derives each window's program/panel/title from the managed-window registry (`readRegisteredLayoutWindow`) with a `KNOWN_WINDOWS` fallback for app-level windows (main/binds/organization-setup/macro-lab/build-layers), and groups them. Each card focuses its window on click and has an X to close it (main is shown but not closeable). It refreshes on open, on focus, and on a ~1.2s poll.
- The main-page top-left action row has a Settings button to the right of Refresh. It opens an in-window Settings dialog (modal overlay) with two checkboxes: "Load last layout on startup" and "Minimize main page on startup". Both settings persist in browser localStorage (`flowcell.startup-settings.v1`, via `FlowCellFrontend/src/lib/startupSettings.ts`). The last successfully saved or loaded layout file path is tracked separately (`flowcell.last-layout-path.v1`) on every successful Save Layout / Load Layout. Save Layout and Load Layout native dialogs are parented to the active FlowCell window and guarded against re-entry so repeated clicks cannot stack hidden file pickers. Layout snapshots store managed window bounds in Tauri's physical desktop pixels and restore those bounds with physical positions/sizes, so mixed-DPI monitors do not shift loaded buttons; Panel Fan's collapsed owner anchor is also persisted/restored in physical pixels, with its DOM-measured owner/expanded geometry scaled only at the native-window boundary, so a fan saved on a 175% monitor does not restore as a huge offscreen/cut-off logical window; single-button script popouts such as `update github` always restore and save with the canonical one-button size so an accidental tall captured window does not keep moving/resizing the button. Script-group popout buttons check the native Windows Space key state on pointer-down, while panel Fan and toolbox/toolset windows poll the same native Space state via `useNativeSpaceDragActive`, so holding Space and dragging an unfocused popped-out button, fan owner, fan child, generic toolset, or dedicated toolbox moves the window instead of first activating the control. On main-window startup, if "Load last layout on startup" is enabled and a tracked layout path exists, FlowCell loads and restores it automatically; load failures are logged and startup continues normally. If "Minimize main page on startup" is enabled, the main window is minimized after startup initialization.
- Panel Fan owner and child slots reserve transparent bottom overflow inside their measured DOM geometry before that geometry is converted to native physical bounds. The skin itself still renders at its normal fan-owner/fan-child height inside the reserved slot, so default popout shadows/text are not clipped at the bottom and the native window no longer needs a second ad-hoc height padding pass. The native cursor hit-test poller also opens or collapses the fan from the live owner/child rects, so transparent click-through windows do not depend solely on DOM pointerenter/pointerleave events. Saved panel-fan sizes are treated as physical collapsed anchors, stale saved fan sizes are ignored when opening, and saved positions are clamped into the current monitor work area before the fan window is shown.

Keep this summary updated whenever FlowCell behavior changes.
